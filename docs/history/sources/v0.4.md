# HorizonWeaver v0.4 里程碑总结

- 日期：2026-08-30
- 版本：v0.4（spec-first：动手前构造带期望输出的测试样例 + done 全样例门控 + 按任务类型差异化构造）
- 状态：**v0.4 结束** —— 结论明确：**spec 实现差**，通过率从 v0.3 的 2/8 **净回归到 1/8**。v0.4 的实验价值不在于通过率，而在于用数据证伪了「弱模型能自造强验收断言」这个假设，为 v0.5 的架构方向提供了依据。

---

## 一、v0.4 的目标

v0.3 冒烟 2/8，6 个失败里 4 个是 `unset`（**假完成**）——agent 自信 emit `done`、判卷失败。根因是 verify 的「做完再写」结构：先有答案、再凑检查，天然可游戏。

v0.4 不碰「放开判卷」（那会改变 benchmark 语义），而是把 verify 升级成 **spec-first**——模型在**动手之前**先根据指令构造一组带期望输出的测试样例并锁定，done = **全部预承诺样例通过**（不再是「任意一条 verify 过」）。这是 TDD「先写测试再写实现」的思路：锁样例时模型还看不到结果，没法「回头洗白」。

按任务类型差异化构造策略：

| 类别 | 特征 | 样例形态 |
|---|---|---|
| target（目标值显式） | 指令写明精确目标（countdown 462） | 断言产物 == 目标值 |
| behavior（行为/症状） | 指令描述「坏了」的症状 | 触发行为、断言症状消失 |
| transform（数据变换） | 指令描述数据变换 | 小输入跑参考、diff 产物 |
| diagnose（分析诊断） | 指令要求跑分析出报告 | 断言报告含关键发现 |

外加**反 trivial 过滤**：`is_surface_check` 禁 `true`/`echo`/纯 `ls`/纯 `test -f`，逼样例做「语义判定」而非「存在性判定」。

---

## 二、实现要点

- **`schema.py`**：新增 `SpecCase`（`command`/`clause`/`category`）与 `ActionKind.SPEC`，`Action` 加 `cases` 字段。
- **`node_agent.py`**：spec 阶段（`step==0` 强制先 spec）→ `validate_spec` 分类校验 → 锁定进 `build_context` → done 门控 v2（引擎跑全部样例，全过才放行）。
- **`tools.py`**：`is_surface_check` + `validate_spec` 纯函数。
- **`system_prompt.py`**：spec-first + 分类构造指令 + 「样例锁定不可改」硬规则。

两个在途引擎 bug 也一并修掉：

- **spec/act 跷跷板**：spec 被拒后下一个 act 会重置 `stuck`，让「连续无进展」永远到不了 8，模型空转直到 harness 900s 超时（broken-python 实测）。修法：spec 锁定后再输出 spec 用**独立 `SPEC_REEMIT_LIMIT=3` 计数**，不被 act 重置，满 3 次干净终止。
- **agent_timeout → 卡顿**：NodeAgent 撞 900s 硬超时会让 harness「executor 线程 join」卡死 1~2.5 小时（jq/countdown-game 实测）。修法：`TIME_LIMIT_S=600` 墙钟上限，在 900s 之前主动干净返回。

## 三、验证结果

### 单测
`python test/run_all.py` 全绿（schema 19 + tools 22 + engine 34 + runtime 13 + plugins 11 + node_agent 5 = **104**，含 B9/B10 回归）。

### 冒烟测试（8 任务）：1/8，净回归

从 v0.3 的 2/8 掉到 1/8。失败不再以「自信 done」的 `unset` 为主，而变成**明确的卡死/被拒**——这本身是个信号：spec 门控确实在工作（把假完成挡在了 done 之外），但代价是模型根本写不出能过的强断言。

---

## 四、失败取证（为什么 spec 实现差）

逐条 context.md 取证，三类典型失败：

1. **首条 spec 是 prompt 示例的逐字拷贝**：7/8 任务的首条样例是 prompt 里「462 示例」的 `assert eval(...)==462`，出现在 jq / broken-python / fix-git / pandas-etl / npm / cprofiling 上——模型没读懂任务，直接把模板抄了。
2. **把探索命令当断言**：fix-git 全锁的是 `git status` / `git log` 这类 diagnose 命令，它们 exit 0 只代表「git 能用」，不代表「修好了」。
3. **恒真 / 不可运行断言**：`grep ... || echo 'no success marker'` 恒真；`import pandas`（容器没装 pandas）不可运行（fix-permissions / pandas-etl）。

**根因不是引擎有 bug，而是架构僵化 + 模型能力天花板**：spec/verify/system2/模型适配器/工具/循环全部硬编码在 `node_agent.py` 一个类里，改任一能力都要动循环，无法「摘掉 spec 做 A/B」来验证「spec 到底是不是负贡献」。这正是 v0.5 要解决的。

---

## 五、结论与 v0.5 方向

**v0.4 达成目标**：用数据证伪了 spec-first 对 9B 模型的假设——**spec 默认关**，净负。价值在于把「假完成 → 明确失败」的形态转变验证清楚了。

**v0.5 方向**：参考 dsh/Cordis 把底层架构改成**即抛即用插件**（每个能力一个组件、经共享 Context 交互、可逆副作用保证卸载干净），spec 从「默认行为」降级为「可装配开关」。详见 `docs/v0.5-plan.md` 与 `开发log/2026-08-30-v0.5-里程碑总结.md`。

**已知天花板**：spec 样例仍由模型自造，「不漏」受限于模型对指令的理解——彻底消除只能放开判卷（改 benchmark 语义，明确不做）。9B 模型的诊断/工具正确性（jq 不用 jq、cprofiling 反复读同一文件）仍是模型层问题，不是架构问题。
