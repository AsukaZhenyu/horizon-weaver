# HorizonWeaver v0.1 里程碑总结

- 日期：2026-08-26
- 版本：v0.1（最小实现验证）
- 状态：**v0.1 结束** —— 骨架已跑通、Terminal-Bench 端到端打通，但真实任务 0/8 通过，暴露出架构缺陷，进入 v0.2。

---

## 一、v0.1 的目标与范围

按 README 的「最小验证原则」，v0.1 只做一件事：**把六步自主探索循环的最小骨架实现出来，并在一套真实终端 benchmark 上跑通端到端**，用最小代价暴露「结构化输入输出 + 图规划路径」这套机制的真实问题。

v0.1 明确**不做**的事（留给后续）：

- index 驱动的回滚/回环（Terminal-Bench 无在线指标，`index` 恒为 `None`，`rollback`/`retrieve` 记为 no-op）；
- 知识经验累积、项目结构建图（README「内容2」）；
- 多模态、GUI 操作（README 明确只做 terminal 内功能）。

## 二、交付物清单

| 文件 | 作用 | 状态 |
|------|------|------|
| `agent/schema.py` | 结构化 I/O：`Action`/`Node`/`Index`/`NodeStatus` + `parse_action`（严格校验 8B 模型易吐的非法 JSON） | ✅ |
| `agent/loop.py` | 独立版六步循环（observe→decide→act→sense→update→loop-closure），状态=git，图=`graph/nodes.jsonl` | ✅ 骨架 |
| `agent/keyan_agent.py` | Terminal-Bench 适配器（`BaseAgent` 子类），harness 真正在跑的入口 | ✅ |

### 六步循环（核心机制）

```
observe(读终端) → decide(模型出 Action JSON) → act(执行命令)
→ sense(读新终端) → update(落图结点) → loop-closure(回环检测)
```

图结点落在 `logging_dir/graph/nodes.jsonl`，每行一个 `Node`：

- **客观字段**（`changes`/`git`/`index`）由 harness 测量，模型不填；
- **主观字段**（`inference`/`reasoning`）由模型填，只用于规划，不用于判定结点好坏；
- 回环检测用 `_state_key`（命令 sha1 指纹），重复命令标记 `REFUTED`。

## 四、调试过程中解决的问题（基础设施层）

v0.1 的大部分时间是和 Windows + 本地模型的环境问题搏斗，这些修复是后续一切工作的地基：

1. **容器路径被 WindowsPath 污染**：`pathlib.Path`（WindowsPath）拼接出的 POSIX 容器路径全错。改为 `PurePosixPath`（`docker_compose_manager.py`、`tmux_session.py`）。

2. **`docker compose up -d` 间歇性挂起**：容器其实已起来，但 compose CLI 进程不退出。两段修复：
   - 临时文件重定向 + 超时 + 进程树击杀 + 重试（`_run_docker_compose_command`）；
   - 超时后向 Docker daemon 确认容器是否 `running`，是则继续而非报错（`start()`）。

3. **asciinema 录像文件锁（`[WinError 5]`）**：`os.replace` 覆盖仍被占用的 `agent.cast` 失败。修复：harness 在测试阶段前 `session.stop()` 提前释放句柄（`harness.py`）+ 替换带退避重试（`asciinema_handler.py`）。

4. **本地思考模型空 content**：Qwen3.5-9B（`qwen35`）在 llama-server 默认 `--reasoning auto` 下，思考 token 路由不稳定，模型吐几个 `reasoning_content` 就 EOS，`content` 恒为空。修复：`--reasoning off`（验证后 3/3 稳定返回完整 JSON）。

## 五、冒烟测试结果

跑了 8 个任务（跨难度、跨类型），**0/8 通过**（唯一通过的是最简单的 `hello-world`，仅作为管道验证，不计入）。

| 任务 | 难度 | failure_mode | 步数 | 关键信息 |
|------|------|-------------|------|----------|
| jq-data-processing | medium | agent_timeout | 100 | **做对 11/14 测试**，只漏 yaml 输出 |
| broken-python | easy | parse_error | 100（仅16条不同） | pip/ensurepip 死循环 |
| fix-git | easy | agent_timeout | 9 | 过早放弃 |
| countdown-game | easy | parse_error | 9 | heredoc 被破坏 |
| pandas-etl | easy | agent_timeout | 13 | 未完成 |
| npm-conflict-resolution | easy | unknown_agent_error | 0 | Docker 404（基础设施） |
| fix-permissions | easy | unset（过早 done） | 2 | 没修权限就报完成 |
| cprofiling-python | medium | unset | 100 | 琐碎命令里循环 |

### 失败模式分布

- `agent_timeout` ×3 —— 撞 900s 超时（多为循环/低效所致）
- `parse_error` ×2 —— 模型吐无法解析的 JSON / 命令被破坏
- `unknown_agent_error` ×1 —— npm 任务 `client/` 子目录 build context + `--no-rebuild` → 容器 404（非 agent 问题）
- `unset` ×2 —— agent「正常」结束但测试没过（过早 done 或纯循环）

## 六、v0.1 结论（关键发现）

**架构能跑通，但真实任务全军覆没。** 三个核心架构缺陷被数据直接坐实：

### P0-1 · 回环检测是空转的

`_state_key` 只把重复结点标成 `REFUTED`，**既不阻止重复执行，也不强制换思路**。证据：

- `broken-python`：100 步只有 16 条不同命令，最后 20 步在 `pip install --upgrade pip` / `ensurepip --upgrade` 间纯循环；
- `cprofiling-python`：100 步一直在 `which python` / `cat` / `mkdir` 里循环，核心交付物 `fast.py`/`fastest.py` 一个没写。

loop-closure 这一环形同虚设——这正是本项目最想解决的「左右脑互博、反复横跳」问题（README 的核心动机）。

### P0-2 · 过早 `done`

`fix-permissions` 只跑了 `cat` + `bash` 两步、没做任何修复就报 done。模型在「卡住/放弃」时输出 done，而不是「任务真的完成」时。

### P1 · 多行命令被破坏

`countdown-game` 用 heredoc 写 Python 求解器，harness 的 `; tmux wait -S done` 被追加进 heredoc 导致 `SyntaxError`。agent 目前只能可靠执行**单行**命令，多行代码/脚本无法可靠下发。

### P2 · 模型本身偏弱（独立于架构）

9B + `--reasoning off`：`parse_error`（吐非法 JSON）、读不懂报错、诊断不到根因（`broken-python` 真实解法是 `get-pip.py`，模型一直没试到）。这是与架构正交的第二层问题。

### 正面信号

`jq-data-processing` 做对了 **11/14** 个测试——jq 变换、过滤、排序、日期格式化全对，只漏了「把参数存成 yaml」这个刁钻要求。说明**结构化 I/O 机制本身能跑通**，瓶颈是「卡住不会换路」和「不会验证再收工」，这恰好是 loop-closure / index 回滚该解决的核心问题。

## 七、v0.2 计划（按优先级）

### 先做（P0：架构 bug，便宜且通用）

1. **回环跳过执行**：`key in seen` 的命令直接跳过，并向模型注入「你已试过 X 且失败，必须换完全不同方法」的强信号。
2. **卡死检测**：连续 N 步全重复 → 判定卡死，干净地终止（返回明确失败），而不是烧满 100 步 / 900s。
3. **done 门控**：禁止第 1-2 步就 done；done 前要求有实际产出证据（TB 无在线指标，至少做「本任务做过 ≥1 次 act」这类最低门槛）。

### 再做（P1：能力补齐）

4. **多行命令支持**：让 agent 把多行代码写进容器脚本文件再执行，或教它用单行 `printf` / `python -c` 规避。

### 单独处理（P2：模型）

5. 试 `--reasoning-format deepseek`（保留推理但正确路由，避开空 content），或用更强模型做真正的 benchmark。模型弱与架构弱要**分开评估**，别让 9B 的能力掩盖架构缺陷。

### 回归验证

修复后用同一 8 任务集重跑对比，目标是先看到 easy 任务（`fix-permissions`、`broken-python`、`pandas-etl`）有非零通过率，再谈扩展到更大任务集。

## 八、对后续战略的结论

回到「跑满 241 个任务 vs 直接下一步开发」的选择：**两者都不是。** 冒烟测试已经证明，在架构 bug 修掉之前，跑更多任务只会重复同样的失败模式（循环、超时、过早 done），没有信息量。下一步是修 P0 的三个架构问题，用同一冒烟集回归验证。
