# HorizonWeaver v0.3 里程碑总结

- 日期：2026-08-29
- 版本：v0.3（分层：Node Agent 基础设施 + System 2 有界可见思考 + 引擎自动推断的上下文）
- 状态：**v0.3 结束** —— NodeAgent 分层落地、System 2 上线，冒烟 **2/8（25%）**（`broken-python` + `fix-permissions`），较 v0.2 的 1/8 翻倍；但暴露出最大问题是「假完成」。

---

## 一、v0.3 的目标

v0.2 把科研探索层（图导航协议、结点三分、科研原则 10 条、精确上下文管理）整套压在了「解决 Terminal-Bench 任务」的执行器上，但 8 个冒烟任务本质都是「修好 pip / 处理 csv / 写对脚本」的小问题，根本用不到图导航；9B 模型反而被科研哲学分散注意力。

v0.3 重新分层，并解决两个在途问题：

| 层 | 职责 | 状态 |
|---|---|---|
| 高层（科研探索） | 结点 + 图导航，需要项目整体知识 | 未来实现（`loop.py` 是雏形） |
| 低层（问题解决）**Node Agent** | 给定已圈定的小任务，把它做出来，无科研/项目知识 | **v0.3 本次实现** |

两个在途问题（承接 v0.2 收尾）：

- **（C）「解出来了但没干净地 emit done」**：模型修好后反复 verify 空转、或 done 被门控拒绝直到卡死。
- **（System 2）「JSON-only 太脆」**：v0.2 要求模型只吐 JSON，弱模型极易吐非法 JSON 或空输出。改为**有界可见思考链**——模型先写简短思考，再输出动作 JSON，引擎从思考里提取动作块。

## 二、架构实现

### 2.1 分层

```
高层 agent（未来，loop.py 雏形）
        │ 调用
        ▼
NodeAgent（node_agent.py）── 无 terminal-bench 依赖，duck-typed session
        ▲
        │ 适配
tb_test（tb_test.py）── 实现 BaseAgent，把 TmuxSession 喂给 NodeAgent
```

### 2.2 文件结构

| 文件 | 作用 |
|---|---|
| `agent/node_agent.py` | **Node Agent 基础设施**（新增，核心）：主循环 + 引擎自动推断 + 上下文组织，不依赖 terminal-bench |
| `agent/tb_test.py` | Terminal-Bench 适配器（由 `keyan_agent.py` 改名瘦身，~50 行）：把 `NodeResult.termination` 映射成 `FailureMode` |
| `agent/schema.py` | 新增 `Attempt`（尝试记录三元组）；保留 `Action`/`Node`；`_extract_json` 支持 System 2 自由思考 |
| `agent/system_prompt.py` | 新增 `build_node_agent_prompt()`（只留任务级硬规则，删科研层） |
| `agent/tools.py` | 复用 v0.2：`bash`/`write`/`read` + 退出码哨兵 + `done_gate_rejection` |
| `agent/test_v03.py` | 单测（`_summarize_attempt` / `build_context` / `Attempt` 序列化） |

### 2.3 核心新机制：引擎自动推断的上下文

**上下文 = 所有尝试的 `(action, result, inference)` 三元组**，其中 `inference`（这一步意味着什么、下一步往哪走）由**引擎确定性生成**（`summarize_attempt`），不让弱模型自己反思：

- bash/verify：`0`→「成功」；`127`→「命令未找到(127)」；`None`→「无退出码（可能超时/截断）」；其他→「失败({ec}) {错误行}」。
- 错误行抽取（`extract_error_line`）优先取含 `Error|error|Traceback|No module|not found|No such` 的行。

`build_context` 把全部尝试组织成「目标 → 已尝试（动作→结果→推断）→ 下一步输出动作 JSON」，超预算时最旧压缩为 `…(前 N 步省略)…`。

### 2.4 System 2：有界可见思考 + 动作提取

- `_extract_json` 从**后往前**找 `{"action"` 起点做括号配对，取最后一个配对成功的对象——思考文字里的杂散大括号 / JSON 示例 / write 围栏代码块都不会干扰提取。
- `_call_model` 处理思考版模型的 `reasoning_content`：当 `content` 无 `{` 而 `reasoning` 有 `{` 时，退回 `reasoning` 取动作。
- `_call_model_with_retry`：空输出重试 4 次（思考早停导致 content 为空）。
- `MAX_OUTPUT_TOKENS=8192`（reasoning 与 content 共享该预算）。

### 2.5 保留的 v0.2 硬保证

- 工具化（`bash`/`write`/`read`/`verify`）、退出码哨兵（含 B8 剥离自注入哨兵）、去重三表（`seen_commands`/`seen_writes`/`seen_verifies`）、卡死终止（`STUCK_LIMIT=8`）。
- done 门控（`done_gate_rejection`）：(1) 至少 2 步 (2) 至少一次 `verified=True 且 exit_code==0` 的 verify 证据。

## 四、冒烟测试结果

同 v0.1/v0.2 的 8 任务集，**2/8 通过（25%）**（v0.2 为 1/8）：

| 任务 | 结果 | failure_mode | 用时 | 关键信息 |
|---|---|---|---|---|
| jq-data-processing | ❌ | unset | 8.5 min | JSON 解析失败 + 反复「拒绝 done：无 verify 证据」 |
| **broken-python** | ✅ | — | 12 min | 干净 done，pip 修复 |
| fix-git | ❌ | unset | 3 min | 快速假完成 |
| countdown-game | ❌ | — | 19.5 min | 空输出长考超限（本 session 手动 taskkill 顶出） |
| pandas-etl | ❌ | unset | 5 min | **回归**：v0.2 唯一通过 → v0.3 失败 |
| npm-conflict-resolution | ❌ | unknown | 5 min | 卡死/报错 |
| **fix-permissions** | ✅ | — | 2.5 min | 权限修复 |
| cprofiling-python | ❌ | unknown | 7 min | 卡死/报错 |

### 失败模式分布（关键信号）

- **4× `unset`（假完成）**：jq / fix-git / pandas-etl（+ countdown-game 的空输出前兆）。agent **以为自己完成了**（正常发出 done），但判卷测试没通过。占失败的大头（4/6）。
- **2× `unknown`（卡死/报错）**：npm / cprofiling。agent 没干净收尾。
- **1× 空输出**：countdown-game。hard 数学题，思考版模型长考烧光 token。

### 假完成（unset）的根因

verify 是「做完再写」的：模型先随便干，干完写一条 `verify` 给自己背书——**先有答案，再凑检查**，天然可游戏。而真正客观的标准（任务自带的 `run-tests.sh`→`pytest`）在 solve 阶段被 harness 物理藏起（`terminal_bench/harness/harness.py:544 _setup_test_env` 只在 grading 时才把 `/tests` 注入容器），agent 客观上够不到。

对照 v0.2：`pandas-etl` 在 v0.2 走「读数据→绕开缺依赖→verify」路径通过，v0.3 重写后**这条成功路径退化**——verify 门控没变，但 NodeAgent 的上下文组织/推理流程让模型没能复现同样的解题路径。这是一个需要单独留意的回归。

## 五、附注：Docker 运维根因（本 session 排查）

冒烟期间 Docker Desktop 反复 npipe 读超时，排查确认是**内存争用**：llama-server 即便 `-ngl 99` 全 GPU offload，进程 working set 仍占 ~5GB 系统 RAM（mmap 出的模型文件页，Windows 不主动回收），把 15.2GB 压到 <1GB free，Docker 的 WSL2 后端疯狂 swap。修复 = `SetProcessWorkingSetSize(-1,-1)` 裁剪 working set。详见 `knowledge/experience/docker-host-memory.md`。

## 六、结论与 v0.4 方向

**v0.3 达成目标**：分层落地（NodeAgent 与科研层解耦）、System 2 上线、引擎自动推断上下文，通过率 1/8 → 2/8。

**但最大瓶颈从「架构弱」转向了「假完成」**：6 个失败里 4 个是 agent 自信 done、判卷失败。verify 机制（自写、exit 0 即算证据、做完再写）无法区分「真的做对」和「凑出一条能过的检查」。

### v0.4 方向：验收标准前置（spec-first verify）

核心：让模型在**动手之前**先根据文字描述构造一组**带期望输出的测试样例**（ACM 技巧：不重不漏、覆盖极端/黑天鹅）并锁定，done 门控 = **全部预承诺样例通过**（而非「任意一条 verify 过」），并按任务类型差异化构造策略（目标值显式 / 行为症状 / 数据变换 / 分析诊断四类），加反 trivial 过滤（拒 `true`/`test -f`/`echo`）。详见 `docs/v0.4-plan.md`。

**已知天花板**：条件仍由模型自写，其客观性受限于「指令是否写清验收标准」——countdown-game 写了「算到 462」能接近客观，broken-python 只说「pip 坏了」只能打补丁。这个边界在 v0.4 计划里写明。
