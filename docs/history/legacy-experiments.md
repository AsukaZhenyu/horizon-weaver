# v0 和 v1 实验总结

2026 年 10 月 20 日归档。Horizon Weaver 从本次清理开始转向基于 Cordis 的可学习执行结构。旧实现停止维护，其实验用于解释问题和确定评测边界。

旧版本证明了环境执行、轨迹存储和部分检查机制可以实现，但没有证明不断增加上下文规则与 Verify 门槛能稳定提高任务完成率。新原型需要学习和比较策略，而不是继续把失败案例逐项变成运行时规则。

## 实验范围和计分

v0 的八项任务与 v1 的八项任务不是同一集合，预算、协议和基础设施也不同，不能横向排成性能排行榜。v1 主要使用 Qwen3.5-9B Q4_K_M、本地 llama.cpp、16k 上下文，常见限制为每任务 40 步、300 秒。具体设置以各轮原始报告为准。

这些任务被反复用于开发，属于开发冒烟，不能继续充当新架构的未知测试集。八项单次运行也不足以证明稳定因果收益。

- **整项通过率**：独立 TB 检查全部通过的任务数 / 全部启动任务数。即使 Agent 超时，遗留产物也可能被外部评分判为正确。
- **正常提交且通过率**：同时满足运行时正常提交和整项通过的任务数 / 全部启动任务数。
- **检查通过数**：通过的单项断言数。它不能替代任务通过率；不同任务的断言数量并不相等。
- **Agent 时间**：通常不含容器准备、外部评分和清理。各轮重复动作指标口径有变化，不跨口径直接比较。

## 反复出现的问题

### 记录完整不等于策略会使用记录

dev11 中，任务认识交付了 134/142 次，但模型没有更新任务认识，历史查询为 0。后续 dev12 引入有证据的认识更新，相同后果失败重复却由 6 增至 21。信息可见、接口被调用和最终收益必须分别衡量。

### 局部测试不足以支持任务完成

SQLite 恢复任务曾只检查 JSON 格式，未验证恢复值；异步任务保持 async 接口仍不满足取消与清理；JQ 的转换结果接近正确但入口脚本或参数记录不满足要求。证据存在、引用有效和状态新鲜不能证明测试谓词充分。[最终逐项分析](sources/v1.3-dev19-findings.md)

### 更强门控可能消耗正确候选的剩余预算

dev14 R16 的四个最终产物通过外部评分，但正常提交且通过为 0/8，总时间上升至 2358.5 秒。继续检查、停滞判断与收尾策略都可能影响结果。不能把外部正确产物计作自主流程已经高效完成。

### 工程正确性和任务能力没有同步增长

v1.3 最后一次报告已有 302/302 回归和真实模型协议探针，TB 仍为 3/8。回归检查的是已编码的执行与协议性质，不是模型是否选对探索方向，也不是一般任务完成能力。

### 实验不足以定位单一根因

模型协议截断、工具超时、Docker 与评分依赖异常确实发生过；大量重复读取、无变化写入和无效自检也存在。缺少多次独立运行与匹配预算的学习对照，不能把所有失败归于模型、上下文或 Verify 中的任一项。

## 新原型保留的原则

1. 只固定操作语义、引用与版本、资源记账和独立验收边界。上下文选择、探测方式、组件功能与协作流程由可替换程序表达。
2. 原始观察和模型解释分开保存。自生成测试作为观察，独立验收负责实验评分；提交不要求满足某种固定反思格式。
3. 保存失败候选，并用匹配预算的实际执行比较候选。归档轨迹本身不称为学习；新任务实际复用和改善才是研究对象。
4. 先证明完整闭环可运行，再采集数据。最终成功率、正常提交率、探索成本与部署成本分别报告。
5. 旧八项只用于开发回归，新测试任务提前划分；不选择最好批次或把不同源码的局部结果合成一个成绩。

## 归档与恢复

清理前的 v0 Git HEAD 为 `731b86e`，v1 主要是未提交工作。v0 的完整历史统一保存在 `claude-code/legacy-v0`，原 `v0.1`、`v0.2`、`v0.3`、`v0.5` 分支名称已清理，所有提交仍可从归档分支访问。v1 快照保存在 `codex/legacy-v1`。

旧代码、测试、脚本、示例与依赖清单也保存在本地 `.legacy/` 的 ZIP；其清单记录文件 SHA-256 和 ZIP SHA-256。完整运行记录保留在本地 `runs/`，第三方源码、书籍和研究资料不删除，也不随新代码上传。

本目录的 `sources/` 保存上述原报告的只读副本，`sources/manifest.json` 记录原路径和 SHA-256。原报告保留当时结论；本总结明确修正证据不足的判断。原报告中的相对附件链接仍可能指向仅在本地 `runs/` 存在的文件。
