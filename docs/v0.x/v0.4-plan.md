# HorizonWeaver v0.4 计划：构造测试样例做 verify（spec-first + 按任务类型差异化）

- 日期：2026-08-29
- 版本：v0.4（spec-first：动手前构造带期望输出的测试样例；done 全样例门控；按任务类型差异化构造策略）
- 状态：**计划**（待实现）

---

## Context（为什么做这个）

v0.3 冒烟 2/8，6 个失败里 4 个是 `unset`（**假完成**）——agent 自信 emit `done`、判卷测试失败。根因是 verify 的「做完再写」结构：

1. 模型先随便干，干完写一条 `verify` 给自己背书（先有答案，再凑检查），天然可游戏；
2. `verified` 门槛极低——`exit_code == 0` 只代表「这条命令没报错」，不代表「任务目标达成」；`verify true` / `verify test -f output.txt` 都能过；
3. 真正客观的标准（任务自带的 `run-tests.sh`→`pytest`）在 solve 阶段被 harness 藏起（`harness.py:_setup_test_env` 只在 grading 时注入 `/tests`），agent 够不到。

v0.4 不碰「放开判卷」（那会改变 benchmark 语义），而是把 verify 从「做完再写」升级成「**动手前构造测试样例**」，采用 ACM 核心技巧——**不重不漏、覆盖极端/黑天鹅、带期望输出**，逼近 test-first / TDD。

**关键认知**（来自本 session 的失败分析）：假完成**全部发生在 produce 任务**（countdown-game / jq / pandas-etl），而 produce 任务的正确性恰好是**自包含可检验的**（跑产物、对照指令里的目标值）。repair 任务（broken-python / fix-permissions）天然靠症状检查就过了。所以「构造测试样例」精准打在失败的那一类上。

---

## 目标（交付物）

1. **spec-first 测试样例构造**：模型拿到指令后，第一轮先输出一组带期望输出的测试样例，锁定进上下文，再开始解题。
2. **done 门控 v2**：done = **全部预承诺样例通过**（不再是「任意一条 verify 过」）。
3. **反 trivial / 分类校验**：引擎按任务类别校验样例（禁 `true`/`test -f`/`echo`，且要求样例是「语义检查」而非「表面检查」）。
4. **按任务类型差异化**：不同类别的任务用不同的样例构造策略（见下）。

---

## 不同任务类型的 spec 策略（核心）

分类维度 = **验收标准的可检验性**：模型的测试样例能多客观，取决于「正确」能否用一条自包含命令判定。

| 类别 | 特征 | 冒烟任务 | 测试样例形态 | 客观性 |
|---|---|---|---|---|
| **A. 目标值显式** | 指令写明精确目标 | countdown-game（462） | 断言产物 == 目标值 | 高 |
| **B. 行为/症状** | 指令描述「坏了」的症状 | broken-python、fix-git、fix-permissions、npm-conflict-resolution | 触发行为、断言症状消失 | 中高 |
| **C. 变换正确** | 指令描述数据变换 | jq-data-processing、pandas-etl | 小输入跑参考、diff 产物 | 中 |
| **D. 分析/诊断** | 指令要求跑分析出报告 | cprofiling-python | 断言报告含关键发现 | 低 |

### A. 目标值显式（produce + 目标已知）

- 样例 = 直接断言目标值：`python -c "assert eval(open('/app/output.txt').read().strip()) == 462"`。
- **黑天鹅 = "长得对但值错"**：绝不用 `test -f` / 「含数字」这类表面检查，必须真 `eval` 出结果比对上目标。这条样例正是假完成命中的地方——它会「正确地失败」。
- **特殊→一般归纳**：先验证简单子目标（两个数能凑出某中间值），再验证完整 462；每步都用 `eval` 断言，不空跑。
- 构造原则：样例集合 = `{目标断言}` + `{至少一条"表面合法但值错"的反例，证明该断言会失败}`（后者验证断言本身有效，而非恒真）。

### B. 行为/症状（repair）

- 样例 = 行为断言：`python3 -m pip install <某包> && python3 -c "import <某包>"`。
- **不重不漏**：覆盖症状的多个表现（pip 可执行 / pip 能装包 / 装完能 import）。
- **黑天鹅** = 「这个用法好了、换个用法坏」（`python -m pip` 好但 `pip` 脚本坏）——不同调用入口各测一条。
- 天花板：模型不知道判卷用的具体包/具体断言，样例是「症状消失」的**近似**。接受。

### C. 变换正确（produce + 数据变换）

- 样例 = 在**小输入**上跑参考、diff 产物：先 `write` 一个 1–2 行的参考输入，用一条**慢但可信**的路（纯 python / 手工 / 简单工具）算出期望输出，再 `diff` 真实产物。
- **特殊→一般**：先在小子集验证转换逻辑，再跑全量。
- **不重不漏**：覆盖不同字段 / 类型 / 边界（空值、缺字段、重复键、类型边界）。

### D. 分析/诊断（produce + 报告）

- 样例 = 断言报告含关键发现（如「报告里出现函数名 X 与耗时 Y」）。
- 客观性低：模型不知道判卷要的具体发现，只能尽力。标记为天花板，不硬撑。

## 通用构造原则（跨类别）

1. **不重不漏（MECE）**：每条样例针对指令的一个**独立**验收点；合起来覆盖所有显式要求。不凑数（不强求 10 条）。
2. **极端 / 黑天鹅**：针对**这一个具体实例**里最刁钻的点，而不是测一串无关输入。terminal-bench 判卷只考单实例，所以「不同性质」翻译成「交付物的不同方面」，「极端/黑天鹅」翻译成「最难的语义点」。
3. **带期望输出**：每条样例要么内嵌断言（`assert`/`diff`/`cmp`），要么以 exit 0 承载「症状消失」的期望。不允许「只跑不判」的样例。
4. **最小验证原则**：样例数量取「能覆盖所有验收点 + 一条黑天鹅」的最小集，不穷举。验证的目标是「区分对/错」，不是「全面测试」。
5. **特殊→一般**（produce/数学专用）：先在小/简单例上验证规律，再推广到完整目标；每步都验证，不做「一步到位」的赌博。

## 架构

```
指令 → observe
      ↓
   spec 阶段：模型输出测试样例集 → 引擎分类校验（非空/非表面/条数/带断言）→ 锁定
      ↓
   主循环（act/write/bash/read/verify）—— verify 只能跑「已承诺的样例」
      ↓
   done 门控 v2：引擎跑全部 spec 样例，要求全部通过
```

**保留** v0.2/v0.3 引擎硬保证：工具化、退出码哨兵、去重、卡死终止、System 2 有界思考、引擎自动推断上下文。
**改变** verify 的语义：从「模型自由 emit 一条命令」变成「模型只能跑 pre-committed 的测试样例」。

## 文件变更

### 1. `agent/schema.py`

- 新增 `SpecCase` 模型：`id`（序号）/ `category`（`A|B|C|D` 或 `target|behavior|transform|diagnose`）/ `command`（带断言的 bash 命令，exit 0 = 样例通过）/ `clause`（引用指令的哪个验收点）。
- `Action` 新增 `ActionKind.SPEC = "spec"`，`cases: list[SpecCase]`。

### 2. `agent/node_agent.py`（核心）

- **spec 阶段**：`step == 0` 且尚未有 spec 时，强制模型先输出 `{"action":"spec","cases":[...]}`；解析失败重试，直到拿到合法 spec 才进主循环。
- **`_validate_spec(cases)`**：条数软约束 `[2, 6]`（不强求凑数，MECE 优先）；每条非空、非表面、带断言；同类去重；`category` 合法。
- **`is_surface_check(cmd)`**：禁 `true`/`:`/`echo`/纯 `ls`/纯 `test -f`/「非空检查」这类只验「存在/合法」不验「值/行为」的表面检查。
- **分类校验**：A 类命令须含 `assert`/`==`/`test` 具体值；B 类须触发行为（跑工具）；C 类须含 `diff`/`cmp`/断言对照。
- **样例锁定**：`self._spec_cases` 存入状态，每轮注入 `build_context`。
- **done 门控 v2**：done 时引擎依次 `run_bash` 每条 spec case，全部 `exit_code == 0` 才放行；任一失败则反馈「第 i 条样例未通过：{command} → {退出码/错误}」。
- **verify 动作约束**：verify 的 `target` 必须是某条 spec case 的 `id` 或命令；自由新命令被拒（要加样例走 `change_spec`）。

### 3. `agent/tools.py`

- 新增 `is_surface_check(command: str) -> bool` + `validate_spec_case(case) -> str | None`（返回拒绝理由或 None）。
- `done_gate_rejection` 签名扩展（或新增 `spec_gate_rejection`），兼容 duck-typing。

### 4. `agent/system_prompt.py`

- `build_node_agent_prompt()` 增加 spec-first + 分类指令：
  - 「先读指令，判断任务类别（目标值显式 / 行为症状 / 数据变换 / 分析诊断）」；
  - 「按类别构造测试样例：A 断言目标值、B 触发行为断言症状消失、C 小输入跑参考 diff、D 断言报告含关键发现」；
  - 「样例要带期望输出（内嵌 assert/diff 或 exit 0），不要 `echo`/`test -f`/`true` 表面检查」；
  - 「produce/数学任务走特殊→一般：先验证简单子例，再验证完整目标」；
  - 「样例一经锁定不能随意改；done 前引擎会跑全部样例，全部通过才算完成」。

### 5. `agent/test_v03.py`（扩展）

- `is_surface_check`：`true`/`echo ok`/`test -f x`/`ls`/`test -s output.txt` → True；`python -c "assert eval(...)==462"`/`diff ... ref.txt`/`pip install X && python -c "import X"` → False。
- `validate_spec_case`：空命令 / 表面检查 / 类别与命令不匹配 / 无断言 → 拒绝并给理由。
- spec 门控：全过 → 放行；一条失败 → 拒绝并给第 i 条失败信息。

## 关键设计

### spec-first vs spec-after（本方案的核心）

现在（spec-after）：模型干完 → 写一条能过的 verify → done。可游戏。

本方案（spec-first）：模型在**还不知道自己最终能做成什么样的时候**划好验收线 → 之后 done 必须过这条线。模型没法「回头洗白」，因为它锁样例时还看不到结果。这是 TDD 的「先写测试再写实现」。

### 「不重不漏」的诚实边界

「不重」模型相对容易做到（构造不同方面的样例）。「**不漏**」做不到——模型看不见判卷的隐藏要求，漏掉的部分就是假完成的残余。所以本方案**压缩**假完成，不**消除**。对指令自包含的任务（countdown 写了 462）能接近消除；对指令含糊的任务只能打补丁。

### 表面检查 vs 语义检查（反 trivial 的本质）

假完成的根因是模型用**表面检查**（`test -f`/非空/合法语法）替代**语义检查**（值对不对 / 症状消没消）。反 trivial 过滤的本质是：**逼样例做语义判定，而非存在性判定**。分类校验把这一条落到实处（A 要 assert 值、B 要触发行为、C 要 diff 参考）。

### change_spec（防回改洗白）

样例锁定后不能随意改。模型若发现初始样例有误（漏了验收点），须用 `{"action":"spec","cases":[...],"reasoning":"为何要改"}` 重新提交并说明理由，引擎允许**一次**放宽（避免「做完后回改样例把门槛调低」），第二次变更计卡死。**（可选，v0.4 可先不做，先验证主链路。）**

## 已知天花板（诚实边界）

1. 样例仍由模型自造，「不漏」受限于模型对指令的理解——彻底消除只能放开判卷（改 benchmark 语义，v0.4 明确不做）。
2. D 类（分析/诊断）客观性低，样例只能「断言报告含发现」的近似，不作为 v0.4 的验收重点。
3. 空输出兜底（countdown-game 长考烧光 8192 token）与 `unknown`（npm/cprofiling）**不在 v0.4 范围**，属模型能力/卡死问题，单独跟踪。

## 默认决策（如无异议按此执行）

- 条数：软约束 `[2, 6]`，MECE 优先，不强求凑数（9B 模型凑 10 条会灌水「文件存在/非空」）。
- spec 用独立 `ActionKind.SPEC`，样例带 `category` 字段驱动分类校验。
- `change_spec` 放宽一次：v0.4 先做（低成本，且能防止「回改洗白」），若实现复杂度超预期可降级为「锁定后不可改」。
- 分类命名用语义化的 `target / behavior / transform / diagnose`（而非 A/B/C/D），便于模型理解与 prompt 复用。
