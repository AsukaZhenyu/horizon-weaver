# HorizonWeaver v0.5 计划：mini-Cordis 插件化底座

- 日期：2026-08-30
- 版本：v0.5（参考 dsh/Cordis 改底层架构：spec/verify/system2/模型适配器/工具/循环全部拆成即抛即用插件，经共享 Context 交互）
- 状态：**已实现**（单测 104 全绿 + fix-permissions 冒烟恢复通过）

---

## Context（为什么做 v0.5）

v0.4 的 spec-first 实验结论明确：**spec 实现差**——弱模型写不出强验收断言。实测（context.md 逐条取证）：
- 7/8 任务首条 spec 是 prompt 里「462 示例」的逐字拷贝（`assert ...==462` 出现在 jq/broken-python/fix-git/pandas-etl/npm/cprofiling 上）；
- 把 `git status` / `git log` 这类**探索命令当断言**（fix-git 全锁的是 diagnose 命令）；
- 写 `grep ... || echo 'no success marker'` 这类**恒真**、或 `import pandas`（容器没装 pandas）这类**不可运行**的断言（fix-permissions / pandas-etl）。

通过率从 v0.3 的 2/8 净回归到 1/8。两个引擎 bug（spec/act 跷跷板、agent_timeout→卡顿）已修，但根因是**架构僵化**：spec/verify/system2/模型适配器/工具/循环全部硬编码在 `node_agent.py` 一个类里，改任一能力都要动循环，无法「摘掉 spec 做 A/B」。

v0.5 参考 dsh/Cordis 改底层架构：每个能力做成**可插拔组件**，通过共享 Context 交互，执行流由组件组合而成。目标（用户原话）：像 vimrc→neovim，各模块独立优化更方便，可自行定义组件、组件与 ctx 交互、组件间交互、执行流，**逼迫各组件低耦合高内聚**。

---

## 目标（交付物）

1. **mini-Cordis 底座**：`Context`（服务总线 + 事件总线 + 可逆副作用）+ `Plugin`（声明式契约）+ `Runtime`（拓扑装配），零新依赖。
2. **把 v0.4 的硬编码能力拆成 7 个插件**：llm / tools / systemPrompt / system2 / verify / spec / agentLoop。
3. **spec 默认关**（v0.4 结论净负），开 = `build_default_plugins(enable_spec=True)`，不改源码做 A/B。
4. **对外门面不变**：`NodeAgent` 名与 `run(instruction, session, logging_dir)` 签名不动，`tb_test` 改动最小。

## 核心抽象（mini-Cordis，~150 行，零新依赖）

### Context —— 服务总线 + 事件总线 + 副作用账本

```python
class Context:
    # 服务：调用方只认 key 不认实现（换 LLM/tools 不改循环）
    provide(key, value) / get(key)
    # 事件：组件间交互的媒介
    on(event, fn) / off(event, fn)
    emit(event, *a)        # 通知，不等结果（markers/日志）
    waterfall(event, *a)   # 中间件链，fn 返回 None 委托下一环，返回非 None 短路（done 门控 / 动作认领）
    collect(event, *a)     # 收集所有非 None 返回值（prompt-section 汇总）
    # 可逆副作用：「即抛即用」的关键，卸载自动回退
    effect(cleanup) / dispose()   # dispose 逆序跑 cleanup
```

### Plugin —— 组件声明式契约

```python
class Plugin:
    name: str
    provides: list[str] = []   # 暴露的服务 key（如 ["llm"]、["spec"]）
    requires: list[str] = []   # 依赖的服务 key（如 ["tools"]、["llm","tools","systemPrompt"]）
    def setup(self, ctx): ...  # 启动：provide 服务 / ctx.on 订阅事件 / ctx.effect 记副作用
```

### Runtime —— 装配器

读所有 Plugin 的 provides/requires，**拓扑排序**决定 setup 顺序（依赖先就绪）；`start()` 依序 `setup` 返回 ctx，`stop()` → `ctx.dispose()`。重复 name/provider、缺依赖、成环 → `RuntimeError`。

## 插件清单（v0.5 首版，从 node_agent.py 拆出）

| 插件 | provides | requires | 职责（迁移来源） |
|---|---|---|---|
| `LlmPlugin` | `llm` | `thinking` | `_call_model` / `_call_model_with_retry` / reasoning 回退 / `_count_tokens` |
| `ToolsPlugin` | `tools` | — | `run_bash`/`write_file`/`read_file`/`with_exit_marker`（tools.py） |
| `SystemPromptPlugin` | `systemPrompt` | — | prompt 骨架 + 汇总各能力插件的 prompt_section |
| `System2Plugin` | `thinking` | — | 「先思考后输出 JSON」prompt 段 + `ctx.thinking` 预算配置 |
| `VerifyPlugin` | `verify` | `tools` | 拥有 VERIFY：自由断言 + 去重 + done 证据门控（v0.3 语义） |
| `SpecPlugin` | `spec` | `tools` | 拥有 SPEC：预提交样例 + done 全过门控（v0.4 语义，**默认关**） |
| `AgentLoopPlugin` | `agentLoop` | `llm,tools,systemPrompt` | 主循环（observe→decide→act→sense），决策全部委托事件 |

未来工具插件（`websearch`/`localfilesearch`）：`requires=["tools"]`，`setup` 里往 `ctx.tools` 注册新 tool，循环零改动。

**组件间交互范式**（用户要的「组件与 ctx / 组件间交互」）：
- `System2Plugin` provide `ctx.thinking`，`LlmPlugin` require `ctx.thinking`——组件经 ctx 传递配置，互不引用。
- `SpecPlugin` provide `ctx.spec`（已锁定样例状态）；`VerifyPlugin` 处理 VERIFY 时 `ctx.get('spec')` 判断是否存在，从而在「自由断言」与「必须匹配 spec 样例」之间切换——组件经 ctx 读对方，不直接 import。

## 执行流如何「可定义」

主循环骨架固定（observe → 组 prompt → 调 llm → 解析动作 → 分发 → 记录），但**每一环行为由订阅的插件决定**：

```python
for step in range(max_steps):
    prompt = ctx.get("systemPrompt").assemble()          # 骨架 + Σ 各插件 prompt_section
    raw = ctx.get("llm").complete(messages)              # 换模型 = 换 ctx.llm
    action = parse_action(raw)                           # schema 词汇不变
    if action == DONE:
        rej = ctx.waterfall("gate-done", ...)            # 各插件逐个放行/拒绝
        if not rej: return done
    handled = ctx.waterfall("handle-action", action, ...) # 插件认领动作（verify/spec/新工具）
    if handled is None:
        dispatch(ctx.get("tools"), action)               # 兜底 bash/write/read
    ctx.emit("after-result", ...)                        # 观察（markers/日志）
```

- 「摘掉 spec」= 不装 SpecPlugin；「加 websearch」= 装一个工具插件。A/B 对比不改源码、可逆副作用保证卸载干净。
- 骨架顺序如后续想重排（先 retrieve 再 act），v0.6 再把 stage 列表做成可注入；v0.5 固定骨架、可插拔决策。

## 验证

1. **单测**：`python test/run_all.py` = **104 全绿**（test_schema 19 + test_tools 22 + test_engine 34 + test_runtime 13 + test_plugins 11 + test_node_agent 5，含 B9/B10 回归）。
   - 覆盖：Context（provide/get/on/off/emit/waterfall/collect/effect/dispose）、Runtime（拓扑排序 / 重复 name / 重复 provider / 缺依赖 / 成环 / 逆序回退）、插件装配（spec 关→verify 门控；spec 开→spec 门控）、spec-off 语义（自由断言 + done 证据门控）、spec-first 语义（前置门控 / 跷跷板 / 墙钟上限）。
2. **回归**：104 全绿不破（schema/tools/engine/runtime/plugins/node_agent 各就其位）。
3. **冒烟**：先跑 fix-permissions（v0.3 通过题，验证 spec 关后恢复）。**结果：恢复通过**（`test_script_permissions: passed`）——顺带修掉两个 Windows 陷阱（见下），全 8 任务冒烟在进行中。

### 冒烟中暴露并修复的两个 Windows 陷阱

- **B9（write_file CRLF）**：`write_text` 在 Windows 文本模式把 `\n` 翻成 `\r\n`，写进 Linux 容器脚本报 `$'\r': command not found`。改 `tmp_file.write_bytes(content.encode("utf-8"))`。
- **B10（read 哨兵泄漏）**：文件末行无换行时，harness 退出码哨兵拼到内容行尾（`echo okKEYAN_EXIT_CODE=0`），`_clean_bash_output` 整行丢弃吞内容、且 READ 分支直出把哨兵当文件内容，模型误判「文件混入哨兵」反复 rewrite。改「只剥哨兵值、保留内容」+ READ 分支走 `_clean_bash_output`。

## 关键设计

### 为什么默认关 spec

v0.4 证明 spec-first 净负，但「摘掉 spec 做 A/B」在旧架构要改循环。v0.5 把它变成装配开关：默认集 = `llm + tools + systemPrompt + system2 + verify + agentLoop`（spec 关 → v0.3 语义），要复现 v0.4 只需 `enable_spec=True`。后续新增能力（websearch / 本地文件检索）同样是「装一个插件」，不碰循环。

### 低耦合高内聚怎么「逼」出来

- 组件只经 `ctx` 交互：provide 服务给下游、`ctx.get` 读上游、`on/waterfall` 订阅事件、`effect` 记可逆副作用，**没有一个插件 import 另一个插件**。
- 每个插件 owns 一个能力（verify 拥有 VERIFY、spec 拥有 SPEC），动作分发走 `waterfall("handle-action")` 认领，兜底才是通用 tools。
- 卸载 = 不装配 + `dispose()` 逆序回退副作用，保证「即抛即用」。

1. 插件化不改模型能力：9B 模型的诊断/工具正确性（如 jq 任务不用 jq、cprofiling 反复读同一文件）仍是模型层问题，不是架构问题。
