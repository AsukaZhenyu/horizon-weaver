## 1. 背景与问题

v0.x 主要由个人需求驱动，采用“先做最小单文件实现，再根据运行问题连续打补丁”的方式推进。它快速验证了本地小模型 Agent 的基本可行性，也暴露了若干关键问题：

1. 工具、循环、提示词、验证和状态管理相互纠缠，一个局部修改容易改变整个系统行为；
2. 单元测试通过不等于真实任务可靠，实际运行仍有写文件协议错误、重复读取、假完成和无法干净收尾；
3. 模型行为、Harness 错误、Loop 策略错误和状态记忆错误难以归因；
4. 每个版本同时改变多个机制，难以做可信的消融实验；
5. 运行环境、依赖、模型参数和任务版本没有形成完整的可复现闭环。

v1.0 不继续在 v0.x 上逐点打补丁，而是先明确 Agent 的领域协议、组件责任、依赖方向、数据流和验收标准，再进行实现。

v0.x 的提示词、循环和插件拆分没有形成按本计划设计的领域架构，不能作为 v1.0 的架构基础。旧实现中的工具兼容性经验和失败场景可以转化为新协议的测试；是否复用具体代码，由 v1.0 的组件边界决定，不承担保持旧行为的要求。开发顺序是先完成 v1.0 的实现和验收，再冻结可信版本，最后开展基线评测和机制消融。

## 2. 北极星与产品定义

项目北极星：

> 在消费级硬件和本地小模型条件下，让 Agent 能够可靠完成具有客观验收条件的科研代码与实验执行任务；成功时交付可复现结果，失败时交付可诊断、可恢复的报告，绝不假完成。

v1.0 的最小用户故事：

> 用户提供一个工作区、一项原子任务、允许的操作范围、验收条件和资源预算。Agent 在隔离环境内探索、修改和验证；验收全部通过才报告成功，否则在超时、无进展或外部故障时明确终止并保存完整轨迹。

### 2.1 v1.0 目标

1. 支持人工确认的结构化 Task Contract；
2. 支持本地模型驱动的单步决策和终端工具执行；
3. Harness 返回可靠、结构化的执行事实；
4. Evaluator 独立掌握完成判定权，模型只能申请验收；
5. Progress Monitor 能区分真实进展、信息进展和无效循环；
6. Event Store 能持久化运行事实，进程中断后可以重放和恢复；
7. Context Compiler 能根据当前目标、未满足条件和历史失败组织上下文；
8. 所有运行保存代码、任务、模型、参数、环境和轨迹信息；
9. 组件可在每次 run 启动前组合和替换，支持后续消融实验。

### 2.2 v1.0 非目标

以下内容不进入 v1.0 核心范围：

- 自动选择研究方向或提出论文贡献；
- 多 Agent 协作；
- 复杂复合任务的自动分解与并行调度；
- 运行中任意热插拔组件；
- service concurrency；
- WikiSkill 长期技能归纳；
- Predictor 执行前成功率预测；
- 根据任务 JIT 编译 Harness；
- Web UI、插件市场或远程服务化；
- 训练新模型。

这些方向保留在 v2.0 以后，只有在 v1.0 的可信闭环通过验收后才进入实现。

## 3. 设计原则

### 3.1 先可信，再动态

Cordis 的时间可组合性和空间可组合性仍是长期架构参考，但 v1.0 只实现其最小子集：

- **时间可组合性**：setup 失败能够回滚；stop 能释放监听器、文件句柄、线程、容器等资源；
- **空间可组合性**：run 启动前检查 provider/requires 拓扑，缺依赖、重复 provider 和依赖成环立即失败；
- **静态装配**：每次 run 启动前根据配置装配组件；run 进行中组件集合保持不变。

运行时热替换、并发 service 和根据 task 动态编译 Harness 推迟到有真实需求和实验依据后。

### 3.2 合同优先

任务首先被表示为 Task Contract，而不是一段无结构 instruction。所有组件围绕同一合同工作，Evaluator 不接受 Policy 在运行中降低验收标准。

### 3.3 模型没有完成权

模型输出 `done` 只表示“申请验收”。最终完成必须由 Evaluator 根据外部证据判断。

### 3.4 单一状态所有者

- Supervisor 拥有 run 生命周期和预算；
- Loop 拥有单次循环的瞬时控制状态；
- Event Store 拥有持久化事实；
- Harness 拥有外部资源句柄；
- 其他组件只消费输入并返回结果，不直接修改别人的私有状态。

### 3.5 事件只描述已经发生的事实

`ActionExecuted`、`StateChanged`、`CheckEvaluated` 是事件；“请执行下一步”是显式方法调用，不使用隐式字符串事件承担核心控制流。

### 3.6 Graph 是 Event Store 的派生视图

先保存不可变事件，再根据事件构建状态图。Graph 结构以后可以改变，但原始运行事实必须能够重放。

### 3.7 每个新机制必须对应真实失败和可关闭的实验开关

不因为概念流行就增加组件。v1.0 构建期先明确组件责任、协议、不变量和验证场景；验收并冻结 v1.0 后，新增研究机制再记录失败样例、机制假设、最小实现、回归测试和 A/B 配置。

---

## 4. 核心不变量

v1.0 实现必须始终满足：

1. 除 Harness 外，没有组件可以对外部环境产生副作用；
2. 除 Evaluator 外，没有组件可以给出最终 `passed=True`；
3. 除 Supervisor 外，没有组件可以修改 run 的全局预算和生命周期状态；
4. Policy 只返回 Action，不直接调用终端、文件系统或容器；
5. Context Compiler 只读 Task Contract、State Graph 和当前 Observation；
6. Graph 不调用模型、不执行工具、不决定下一动作；
7. Runtime Context 不保存业务 RunState；
8. 所有重要状态变化必须先成为 RunEvent，之后才能进入 Graph 和报告；
9. 同一事件流在相同版本下必须重放出相同的状态和 Verdict；
10. 成功、失败、无进展、超时、模型错误和 Harness 错误都必须形成明确终态。

## 5. 共享领域协议

低耦合的基础不是文件数量，而是稳定、带类型的协议。v1.0 首先定义以下对象：

```python
TaskContract
Action
Observation
ToolResult
StateSnapshot
StateDelta
Evidence
ProgressAssessment
Verdict
RunEvent
RunResult
```

建议的最小语义如下：

```python
class TaskContract:
    goal: str
    constraints: list[str]
    allowed_paths: list[str]
    acceptance_checks: list[Check]
    expected_artifacts: list[str]
    budget: Budget


class Action:
    kind: str
    arguments: dict
    expected_effect: str


class ToolResult:
    exit_code: int | None
    output: str
    error_type: str | None
    duration_s: float


class StateDelta:
    changed_files: list[str]
    changed_metrics: dict
    new_failures: list[str]
    resolved_failures: list[str]


class ProgressAssessment:
    level: str  # none | information | state_change | verified
    repeated: bool
    reason_code: str
    evidence: list[Evidence]


class Verdict:
    passed: bool
    satisfied_requirements: list[str]
    unsatisfied_requirements: list[str]
    evidence: list[Evidence]
```

协议对象尽量不可变并可序列化。组件之间交换这些对象，不共享可任意修改的字典或 `RunState`。

## 6. v1.0 组件划分

### 6.1 Task Contract

定义目标、约束、允许操作、验收条件、预期产物和预算。v1.0 由人提供或确认；模型可以提出补充检查，但不能删除或降低既有要求。

### 6.2 Runtime / Composition Root

负责组件注册、依赖检查、构造和释放。`ctx` 仅承担：

1. 依赖注入；
2. 只读 RunConfig；
3. 生命周期 cleanup。

`ctx` 不保存业务状态，不作为任意字符串事件总线，也不允许组件通过它修改彼此内部状态。业务对象优先使用显式构造参数注入。

### 6.3 Model Gateway

封装本地模型服务差异，包括请求协议、超时、token 统计、空输出、reasoning/content 兼容和模型元数据。Policy 依赖 Model Gateway 接口，不依赖 llama-server/httpx 细节。

### 6.4 Harness

Agent 与环境交互的唯一边界，负责：

- bash/read/write 等工具；
- 终端、Docker、worktree 和文件系统适配；
- 权限、路径、网络和资源限制；
- 退出码、输出、异常和持续时间；
- 执行前后 StateSnapshot 与 StateDelta；
- 可复现的环境元数据。

Harness 只返回事实，不选择策略，也不判断任务是否已经完成。

### 6.5 Evaluator

根据 Task Contract、Evidence 和 StateSnapshot 判断哪些要求已经满足。Evaluator 拥有最终完成权，并区分：

- 观察成功；
- 命令执行成功；
- 功能验收成功。

`cat`、`ls`、单纯 `test -f` 等观察性或表面检查不能自动成为强功能证据。

### 6.6 Event Store / State Graph

Event Store 以 append-only 方式保存：

```text
RunStarted
ActionProposed
ActionExecuted
StateChanged
ProgressAssessed
CheckEvaluated
RunTerminated
```

State Graph 从事件派生：节点表示环境和验收状态，边表示动作、结果与状态增量。它支持当前状态、父节点、重复状态、失败路径、最近有效状态和恢复查询。

首版使用 JSONL 或 SQLite 即可，不引入图数据库。

### 6.7 Context Compiler

根据 token 预算组织本轮推理输入：

```text
任务目标与约束
+ 当前未满足的验收项
+ 当前工作区差异
+ 最近相关错误和证据
+ 已失败的方法
+ 与当前问题相关的文件摘要
```

Graph 保存事实，Context Compiler 决定本轮看什么；两者不能合并。

### 6.8 Policy

根据编译后的 DecisionInput 返回下一 Action。System Prompt、System 2、动作 schema、模型选择和决策策略属于 Policy。

最小接口：

```python
decide(decision_input: DecisionInput) -> Action
```

### 6.9 Progress Monitor

确定性判断本步是否产生有效进展：

- 新错误、新证据：information；
- 有目标相关的环境变化：state_change；
- 验收项由失败变通过：verified；
- 重复读取、等价改写、无新信息命令：none。

Progress Monitor 只测量，不负责解释和选择下一行动。

### 6.10 Failure Reasoner

当 Progress Monitor 返回无进展或 Harness/Evaluator 返回失败时，基于结构化事实产生简短原因和下一轮约束。它可以先使用确定性规则，必要时再调用模型。

Reasoner 不得覆盖 Progress Monitor 的客观结论。

### 6.11 Loop

Loop 是唯一流程编排者，负责按固定骨架调用各接口，但不实现接口内部逻辑：

```python
while supervisor.can_continue():
    before = harness.snapshot()
    history = graph.query(task, before)
    context = context_compiler.build(task, before, history)

    action = policy.decide(context)
    result = harness.execute(action)
    after = harness.snapshot()

    progress = progress_monitor.assess(before, action, result, after)
    verdict = evaluator.assess(task, result, after)
    event_store.append(...)

    if verdict.passed:
        return success
    if progress.requires_stop:
        return blocked
```

### 6.12 Supervisor

管理整个 run：run_id、预算、墙钟时间、最大步骤、中断恢复、外部故障、终态和最终报告。回环检测的客观信号来自 Progress Monitor/Graph，Supervisor 决定是否停止或恢复。

### 6.13 Reporter / Event Sink

替代含义模糊的 `std-io`。内部组件只交换结构化对象，Reporter 决定如何输出：

```text
RunEvent -> ConsoleReporter
         -> JsonlReporter
         -> TerminalBenchReporter
```

Reporter 只观察事件，不反向修改业务状态。

## 7. 依赖方向

```text
core protocols           不依赖任何业务模块
task contract            只依赖 core
harness/model adapters   实现 core 中的 port
event store              只持久化 core 类型
state graph              从 event store 派生
context compiler         只读 task + graph + observation
policy                   只依赖 context + model port
progress monitor         只依赖 before/action/result/after
evaluator                只依赖 contract + evidence/snapshot
loop                     依赖以上接口，不依赖具体实现
supervisor               管理 loop 生命周期
reporter                 订阅 RunEvent，不反向影响业务
```

禁止出现：

- Harness import Loop；
- Graph import Policy；
- Evaluator 修改 Task Contract；
- Policy 直接调用 session；
- 多个插件共同修改同一个 RunState；
- 用 `ctx.get("...")` 和字符串事件隐藏核心业务依赖。

## 8. 一次运行的数据流

1. Supervisor 创建 run，加载 Task Contract 和 RunConfig；
2. Runtime 验证依赖拓扑并装配组件；
3. Harness 初始化隔离环境并产生初始 StateSnapshot；
4. Event Store 写入 `RunStarted`；
5. Context Compiler 从任务、当前状态和历史构建 DecisionInput；
6. Policy 经 Model Gateway 产生 Action；
7. Harness 执行 Action，返回 ToolResult、StateSnapshot 和 StateDelta；
8. Progress Monitor 判断是否有有效进展；
9. Evaluator 更新要求满足情况并给出 Verdict；
10. Event Store 记录完整事实，State Graph 更新派生视图；
11. Failure Reasoner 在失败或无进展时生成下一轮反馈；
12. Loop 继续，或由 Evaluator/Supervisor 进入明确终态；
13. Reporter 生成终端输出、JSONL、补丁和最终报告；
14. Runtime 逆序释放资源。

### M0：确认架构边界与验证场景（1～2 天）

任务：

- 确认第 4～8 节的核心不变量、共享协议、组件所有权和数据流；
- 为成功、验收失败、无进展、超时、模型错误、Harness 错误和恢复定义验证场景；
- 将旧实现暴露的写文件协议、重复读写和假完成问题转化为通用协议场景；
- 明确唯一 Python 环境、依赖清单和新实现入口；
- 选择一个人工 Task Contract 和确定性 Policy，作为首个可运行闭环。

退出条件：组件的输入、输出、状态所有者和副作用边界明确；首个闭环的验收条件可执行。v0.x 的冻结、成功率复跑和基线比较不作为开发前置任务。

### M1：共享协议与最小 Runtime（2～4 天）

任务：

- 定义核心 dataclass/enum/Protocol；
- 实现序列化和 schema 版本；
- 将 ctx 限定为装配、只读配置和 cleanup；
- 实现启动前依赖检查；
- 建立组件 contract test。

退出条件：组件可以用假实现装配；缺依赖、重复 provider、成环和 setup 回滚均有测试。

### M2：可信 Harness 与 Model Gateway（3～5 天）

任务：

- 统一 bash/read/write 返回结构；
- 按新 Action 协议传递文件内容，保证动作描述与文件 payload 分离；
- 固化退出码、超时、CRLF、哨兵和输出截断回归；
- 实现前后快照和最小文件状态增量；
- 隔离本地模型 HTTP 适配。

退出条件：使用假 Policy 可稳定执行工具；Harness 错误不会被误报为任务成功。

### M3：Event Store、重放与最小 State Graph（3～5 天）

任务：

- 定义 RunEvent；
- append-only 保存事件；
- 从事件重建当前状态；
- 添加状态指纹、父节点和动作边；
- 支持进程重启后的只读重放和继续运行。

退出条件：同一事件流重放得到相同状态；损坏或不兼容 schema 能明确失败。

### M4：Evaluator、Progress Monitor 与 Failure Reasoner（4～7 天）

任务：

- 实现人工 Task Contract 和要求追踪；
- 将 done 改为申请验收；
- 区分观察、执行成功和功能证据；
- 根据输入状态和文件版本检测重复 read、等价 write、无新信息命令和验收无变化，允许状态变化后的重新读取和重新验证；
- 验收证据绑定受检状态，产物变化后重新检查；
- 对无进展产生短反馈，不让 Reasoner 改写客观结论。

退出条件：通用假完成与重复读写场景被正确识别；修改产物后不能沿用旧验收结论；无进展任务能干净终止。

### M5：最薄 Loop、Policy、Context Compiler、Supervisor（5～8 天）

任务：

- Loop 只保留显式编排；
- Policy 封装 prompt、模型调用和 Action 解析；
- Context Compiler 使用目标、未满足条件、最新证据和失败路径；
- Supervisor 管理预算、超时、中断和终态；
- Reporter 输出人类报告和机器可读记录。

退出条件：使用假模型可覆盖成功、失败、无进展、超时、模型错误、Harness 错误和恢复场景。

### M6：真实模型集成与 v1.0 验收（5～10 天）

任务：

- 接入本地 7～9B 模型；
- 在人工合同定义的原子任务上验证新架构的完整闭环；
- 对验收任务重复运行，检查执行事实、证据、终态和资源释放；
- 在 5 个真实科研原子任务上持续使用；
- 修复只由通用机制能够解释的问题，不为单题写特例。

退出条件：达到第 11 节的 v1.0 验收门槛。

### M7：验收后冻结 v1.0 并建立基线

这是 v1.0 完成后的独立阶段，不阻塞 M0～M6 的实现。

任务：

- 冻结已验收的 v1.0 代码、领域协议、默认组件配置和运行环境；
- 建立研究开发集与 holdout 集，记录模型、任务和预算设置；
- 重复测量成功率、假完成率、无效动作、恢复、时间和 token 成本；
- 以 v1.0 为首个架构基线，开展上下文策略及后续状态机制的单变量消融；
- v0.x 的历史结果仅用于解释失败来源，不承担正式基线角色。

退出条件：v1.0 的固定配置可复现，正式评测和后续机制比较有统一的参照。

## 11. v1.0 验收门槛

### 11.1 工程门槛

- 默认环境能够按文档一键安装并运行；
- 单元测试、组件 contract test、事件重放测试和场景测试全部通过；
- setup/stop 后没有残留资源；
- 所有终态都有结构化 RunResult 和最终报告；
- 进程中断后可以从最后一个完整事件恢复；
- 每次 run 保存代码版本、Task Contract、模型、模型参数、环境和事件轨迹。

### 11.2 可靠性门槛

- 开发集和真实任务集的假完成率为 0；
- 成功、失败、超时、无进展和外部错误均能 100% 干净收尾；
- 重复读取和语义等价改写不能无限重置卡死计数；
- Evaluator 的通过结论可以追溯到具体 Evidence；
- 同一轨迹重放产生相同 Verdict。

### 11.3 可用性门槛

- 至少选择 5 个真实、会重复发生的科研原子任务；
- 每个任务独立运行 3 次，共 15 次；
- 至少 60% 的运行无需人工介入完成；
- 未完成的运行能够指出阻塞点、最后有效状态和已失败方法；
- Terminal-Bench 等基准作为回归和横向比较，不作为唯一产品目标。

第一版不追求所有任务成功。可靠失败优先于假成功。

### 11.4 评估指标

- task success rate；
- false completion rate；
- clean termination rate；
- no-progress action ratio；
- repeated read/write ratio；
- wall time；
- input/output token；
- human intervention rate；
- recovery success rate；
- 每个验收项的 Evidence 覆盖率。

## 12. 版本路线图

版本升级由能力和证据门槛触发，不按时间自动升级。

### v1.0：可信的原子任务 Node Agent

产品目标：给定人工确认的 Task Contract，在隔离环境中可靠解决或明确终止一个原子终端任务。

核心机制：

- 稳定领域协议；
- 可信 Harness；
- 外部证据驱动的 Evaluator；
- Progress Monitor；
- Event Store / State Graph；
- 结构化 Context Compiler；
- 可恢复 Supervisor；
- 可消融的 Policy。

潜在研究问题：确定性控制层能否补偿本地小模型的假完成和无效循环。

### v1.x：稳定化与上下文实验

以 M7 冻结的 v1.0 为研究基线，在不扩大任务范围的前提下：

- 增加更多真实原子任务和适配器；
- 比较完整历史、滑动窗口、Attempt Ledger、状态图检索；
- 完善文件/模块摘要缓存与失效机制；
- 提高恢复能力和长时间运行稳定性；
- 形成 v1.0 机制的系统消融数据和论文初稿。

进入 v2.0 的条件：v1.0 验收门槛持续满足，且真实使用证明多个原子任务需要被组织成复合工作流。

### v2.0：科研实验工作流 Agent

产品目标：人定义研究问题、实验意图和关键验收；系统将已确认的复合任务组织为可恢复的任务 DAG，并调用多个 Node Agent 完成代码、实验和结果整理。

新增能力：

- `Workflow Contract` 和人工确认的任务分解；
- 任务 DAG、依赖和关键路径；
- 实验 Job 规范：命令、参数、seed、指标解析、资源预算和产物；
- 多个 Node Agent 的串行/有限并行调度；
- GPU/CPU/时间资源管理；
- 失败节点局部重试，不重跑整个工作流；
- 实验表格、图、补丁和可复现报告；
- 6～12 小时长任务的检查点与恢复；
- 关键决策的人类审批点。

v2.0 不自动决定研究问题或论文结论。人仍然拥有假设、实验设计和结果解释责任。

潜在研究问题：证据驱动的层级控制和可恢复任务图，能否提高本地小模型执行长科研工作流的成功率与资源效率。

进入 v3.0 的条件：积累足够多的任务类型、固定组件配置和运行轨迹，能够证明“不同任务适合不同 Agent 配置”。

### v3.0：自适应 / JIT Agent Runtime

产品目标：根据任务特征生成中间表示，自动选择并组合 Harness、Policy、Context Compiler、Evaluator 和预算配置。

新增能力：

- Task IR：任务类别、风险、工具、验收、上下文和资源需求；
- Harness Compiler：从 Task IR 生成静态运行配置；
- Predictor：执行前预测动作成功率、风险和成本；
- 根据任务选择 Policy、模型、工具和上下文策略；
- WikiSkill：从已验证轨迹中归纳可追溯、可版本化的长期知识与技能；
- 组件级消融和离线策略评估；
- 在证据充分时探索 run 内有限动态替换和 service concurrency；
- 失败轨迹驱动的配置优化，而非直接相信模型自评。

潜在研究问题：JIT 编译的 Agent 配置能否在本地小模型下优于固定通用 Harness，并降低 token、时间和失败成本。

进入 v4.0 的条件：自适应配置在 holdout 任务和多种本地模型上稳定优于固定配置，而不是只对开发集过拟合。

### v4.0：长期科研项目 Agent（远期愿景）

产品目标：围绕一个长期科研项目维护可追溯的项目状态，协助连接文献、代码、实验、数据和文档，但关键科研判断仍由人负责。

可能能力：

- 项目级 Problem/Assumption/Experiment/Evidence Graph；
- 文献、代码模块、实验结果和论文论点之间的引用关系；
- 多工作流协调和跨阶段恢复；
- 自动生成周报、实验记录、消融表和论文材料草案；
- 研究资产版本化和可复现打包；
- 对矛盾证据、缺失实验和不可复现结论进行提醒；
- 人类对研究问题、关键假设、真实实验和论文结论保持最终审批权。

v4.0 以后是否进行模型训练和“结构化推理模型—Agent 系统协同设计”，由 v1～v3 的实验结果决定，不提前承诺版本号。

## 13. 研究与工程记录规范

为了让“能用的产品”和“可发表的研究”共用一套开发资产，每个机制都记录：

v1.0 实现期间先保存协议决策、验证场景和运行事实。正式的基线结果、holdout 评测和机制消融在 v1.0 验收与冻结后开展。

1. 对应的真实失败轨迹；
2. 可证伪的机制假设；
3. 最小实现和配置开关；
4. 单元/回放/场景测试；
5. 开发集和 holdout 结果；
6. 对成功率、假完成、循环、token、时间的影响；
7. 失败边界与负面结果。

每次实验保存 Run Manifest：

```text
code commit / dirty diff
task id + task version + Task Contract
model + quantization + server version
temperature / seed / token budget
component configuration
environment image
events / graph / final verdict / artifacts
```

论文贡献应来自可重复的机制增益，而不是组件数量或架构复杂度本身。

## 14. 当前默认决策

如无新的实验证据，v1.0 按以下默认决策推进：

1. 一个进程内的模块化架构，不做微服务；
2. 每次 run 前静态组合组件，run 内不热插拔；
3. ctx 只做依赖注入、只读配置和 cleanup；
4. Task Contract 由人确认；
5. Evaluator 拥有完成权；
6. Event Store 是事实源，Graph 是派生视图；
7. Progress Monitor 与 Failure Reasoner 分离；
8. Reporter 替代含义模糊的 std-io；
9. WikiSkill、Predictor、Harness Compiler 和 service concurrency 推迟到 v3.0；
10. 先完成 M0～M4 的可信闭环，再接入真实模型优化 Policy；
11. 不为单个 benchmark 隐藏测试写特例；
12. 可靠失败优先于假成功。
13. 先完成 v1.0 架构实现和验收，再冻结 v1.0 并建立基线；v0.x 只保留为探索记录、失败样例和工具兼容性参考。
