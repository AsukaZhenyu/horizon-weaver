# 分析口径与已知偏差

这份文档规定「数字怎么读」。设计见 [`DESIGN.md`](DESIGN.md)，结果表由脚本生成。
凡是结果里出现的偏离，都必须能在本文件里找到对应条目；反过来，本文件写了却没有在结果里标注的，
视为漏报。

## 1 三个量的定义

| 量 | 定义 | 注意 |
| --- | --- | --- |
| A | 冻结后的候选文件系统通过原任务的**全部**检查 | 部分通过不算通过（见 §2.4） |
| V | 预算内按宿主原生协议正常交付：进程正常退出、有最终答复、未触截止期 | 超时/崩溃/被外部杀 = 0 |
| Y | A × V | 主指标 |

- **A = null 不等于 0**：评分没跑起来（容器网络、镜像、脚本自身报错）时记 null，
  该题**不进分母**，并在偏差表里单列。把基础设施失败记成方法失败，是最容易也最不该犯的错。
- V 是「正常提交」而不是「做了事」：Agent 跑满 300 s 但没有任何最终答复，V=0 且 A 不参与 Y。

## 2 两条评分路径

同一轮里两组题走不同路径，这是**协议差异**，逐题报告，不做平均：

### 2.1 历史 8 题（H 层）

沿用 round1–3 的离线协议：暂停容器 → 打包 `/app` → `docker commit` → 在与候选完全相同的
文件系统里，用缓存好的 `uv 0.7.13` + 固定 wheel（pytest 8.4.1 及其 5 个依赖）装环境，
在**无网络**下跑原 `test_outputs.py`。要点：

- 测试文件与 `run-tests.sh` 一字节不改，注入前对内层 `tests/` 做逐文件哈希比对；
- 评分阶段模型调用为 0、Agent 动作为 0；
- 与 round1–3 可比，因为工具链逐位相同。

### 2.2 新 16 题（N 层）

走 `grade_generic`：同样冻结候选，但执行任务**自带的** `run-tests.sh`，因此**需要网络**
（apt 装 curl → astral.sh 装 uv → PyPI 装 pytest）。本机额外做了两处注入，以便在只剩
宿主代理的网络下复现：

1. 评分容器加 `--add-host host.docker.internal:host-gateway` 与 `HTTP(S)_PROXY`
   （默认 `http://host.docker.internal:7890`，可用 `TB_GRADING_PROXY` 覆盖）。
   起因：Docker Desktop 的代理只作用于 daemon，**不注入容器**，镜像构建能走代理、
   容器内 `curl astral.sh` 却直接断（`SSL_ERROR_SYSCALL`），随后 `uv: command not found`。
2. 先把缓存的 `uv 0.7.13` 二进制拷进 `/usr/local/bin/uv`。脚本里那行 `curl | sh` 失败无妨，
   后面的 `uv venv` / `uv pip install` 照原样执行——**测试文件与脚本本身没有改动**。

因此 N 层的评分记录必须带两个标注：**评分容器带宿主代理**、**uv 由宿主缓存注入**。
在网络直连的机器上这两条注入是无操作，但记录里仍会出现，不要把「有代理」读成「任务需要联网作弊」。

### 2.3 评分失败的处理

评分无效（A=null）时用 `--recovery-label <label>` 只重跑评分、不重跑 Agent：
候选镜像 ID 必须与被替换的那次一致，新增模型调用与 Agent 动作必须为 0。
重跑写进 `grading-recovery-<label>/`，原记录保留不删。

### 2.4 计数

`grading.counts` 是原测试自己的 passed/failed 计数。历史 8 题有预注册的检查数
（`protocol.json.expected_checks`），**实际执行数必须与之相等**，否则整题记 A=null——
这能抓住「测试没跑全却被当成通过」这类静默错误。新题没有预注册计数，以脚本退出码
（0/1/5 视为有效执行）与「是否真的收集到用例」为准。

## 3 已知偏差（每条都必须在结果里出现）

| 编号 | 偏差 | 影响 | 处理 |
| --- | --- | --- | --- |
| D1 | 跑的是 TB **0.2.18**，不是 2.1 | 任务集与论文的 TB 2.1 不同 | 结果只能标「TB 0.2.18 分层开发集」 |
| D2 | N 层评分容器走宿主代理 + 注入 uv | 需要联网的题在本机才可评 | 逐题在 `grading` 块标注 |
| D3 | 两条轨道宿主不同（Pi vs 受控终端） | 比较的是**完整集成**，不是组件效应 | 不做组件级归因 |
| D4 | 只有 1 个种子 | 不能估计方差 | 差值区间留给 L1（3 seeds） |

| D6 | 共享镜像 ID 的题目 | `hello-world` 与 `cancel-async-tasks` 内容相同，Docker 去重成一个 ID，后打的标签覆盖前者 | 运行器按**镜像 ID** 引用，不按标签，不受影响 |

## 4 怎么读结果表

- 主看 **Y**，其次 A 与 V：`A=1,V=0` 说明做对了但没在预算内交付，
  和 `A=0,V=1` 是两种完全不同的失败，不能合成一个「不通过」。
- **按层（H/N）和按桶分开看**。H 是长期开发集，N 是分层开发集，两者都不是未见泛化证据。
- n 很小的桶只报描述统计，不给区间。
- `tokens` / `modelRequests` 是成本，不是能力；两者一起看才知道是「答得快」还是「答得少」。

## 5 复现一份历史结果

1. `git checkout` 到产生该结果的提交（`results/<round>/` 与代码在同一提交里）；
2. `bootstrap/setup.ps1 -Check` 看缺什么；
3. `scripts/run_round.ps1 -Status` 会显示该机器上哪些题已有证据；
4. 逐题对比 `results/<round>/<method>/cases/<task>.json` 与本地重新产出的 `result.json`：
   **镜像 ID、模型 sha256、protocol sha256 三项必须相同**，之后才谈数字是否一致。

## 6 本机已做过的冒烟

（2026-10-31，round4 装置首次可用时记录）

- `hello-world` 假候选（直接写 `/app/hello.txt`）→ 快照 → 历史评分路径：
  `valid=true, A=1, counts{passed:2}`，11.8 s。历史路径在搬迁后仍然可用。
- `assign-seats` 假候选（空 `/app`）→ 快照 → `grade_generic`：
  `valid=true, A=0, exitCode=1, counts{failed:2}`，40.2 s。
  pytest 确实跑起来了，空候选正确地两项全失败。

这两条只证明「评分路径能跑通」，不构成任何方法能力证据。
