# Research：科研注意事项

[toc]

> 创建于：2026-08-04  
> 用途：记录硕士阶段做研究时应反复检查的方法、边界与实验纪律。本文不是对过去经历的检讨，而是把已经付出代价获得的经验转化为可执行流程。

## 1. 核心原则

### 1.1 研究不是把系统做出来

完整实现一个复杂系统可以证明工程能力，但不自动构成研究贡献。研究首先需要回答：

1. 发现了什么此前没有被清楚认识的现象？
2. 现有抽象、理论或机制为什么不能充分解释或解决它？
3. 提出了什么新的抽象、模型、机制或范式？
4. 什么证据能够支持或否定这一主张？

理想的贡献链条是：

```text
新观察
→ 新的问题定义或抽象
→ 数学模型与理论边界
→ 新机制
→ 快速模拟验证
→ 必要的真实实现
```

不要采用下面的顺序：

```text
先买硬件或修改大型系统
→ 不断处理实现细节
→ 跑出实验结果
→ 再寻找能够包装成论文的故事
```

实现是验证研究判断的仪器，不应成为产生研究判断的替代品。

### 1.2 真实性不等于研究价值

使用工业界当前的软件栈、真实 GPU 或 FPGA，并不天然比数学模型和模拟器更有意义。不同工具回答不同层次的问题：

| 工具 | 主要回答的问题 |
|---|---|
| 纸笔模型 | 想法是否违反基本上界，理论上是否可能成立 |
| 微基准 | 关键硬件参数和假设是否真实 |
| 离散事件模拟器 | 机制在大范围配置中是否可能有效 |
| Trace 驱动模拟 | 模型能否解释真实工作负载 |
| RTL/Verilator | 控制逻辑在周期级是否正确、能否实现 |
| 综合工具 | 面积、频率、资源占用是否可接受 |
| 真实系统 | 未建模因素是否推翻结论，端到端效果是否成立 |
| FPGA/真实硬件 | 板级 I/O、存储控制器、能耗等物理效果是否成立 |

使用更昂贵的工具，不代表研究更深入。应当使用能够回答当前问题的最便宜工具。

### 1.3 优先证伪，而不是优先证明自己正确

提出想法后，首先寻找能够最快否定它的实验：

- 是否违反带宽、容量、算力或信息论上界？
- 是否已有工作完成了相同的机制？
- 是否只在极少数参数下成立？
- 是否依赖不现实的硬件或工作负载假设？
- 是否只是把开销从一个位置转移到了另一个位置？
- 即使机制完全生效，端到端收益的上限是多少？

如果一个想法能够被简单模型否定，就不应通过数周工程来再次否定。

## 2. 开始项目前必须写清楚的内容

在实现之前，先写一页研究说明。至少包括以下内容。

### 2.1 一句话观察

格式：

> 在条件 C 下，现有系统通常认为 X，但测量或分析表明 Y。

观察必须可以被数据、文献或逻辑验证，不能只是“感觉应该如此”。

### 2.2 一句话研究问题

格式：

> 能否利用 Y，在约束 Z 下，实现或证明 P？

研究问题应当包含明确的对象、条件和目标，而不是“优化 LLM 推理”之类的宽泛表述。

### 2.3 一句话机制

格式：

> 我们将 A 表示为 B，并利用 C 生成 D，从而避免 E。

如果无法用一两句话说清机制，通常说明问题尚未收敛。

### 2.4 可证伪条件

事先写出什么结果意味着想法不值得继续，例如：

- 理论提升上限不足 10%；
- 模拟结果只在单一模型或单一带宽下成立；
- 校准后模拟误差超过 20%；
- 机制依赖无法获得的数据；
- 与最接近工作的差异仅是工程实现；
- 最小原型也必须侵入十几个无关模块。

没有失败条件的项目很容易无限延长。

### 2.5 最小证据

提前规定支持主张所需的最小证据：

- 一个理论上界或 break-even point；
- 一个能够复现实测趋势的模拟器；
- 两到三个有代表性的模型或工作负载；
- 多种硬件参数下的敏感性分析；
- 一个最小真实系统验证；
- 与最接近工作的直接对照。

## 3. 先建立最简单的数学模型

模型不需要一开始就精确。第一版的任务是排除数量级错误，并确定真正的瓶颈。

### 3.1 明确变量和单位

至少列出：

- 数据量：byte/token、byte/layer；
- 带宽：byte/s；
- 延迟：s、ms、us；
- 算量：FLOP/token；
- 算力：FLOP/s；
- 容量：byte；
- 并发资源：stream、slot、queue 数量。

所有公式先做量纲检查。很多不成立的想法会在单位换算阶段暴露。

### 3.2 计算理论上下界

以流式 LLM 推理为例，最简单的传输下界为：

$$
T_{transfer} \geq \frac{D_{weight}+D_{KV}+D_{activation}}{B_{effective}}
$$

计算下界为：

$$
T_{compute} \geq \frac{FLOPs}{P_{effective}}
$$

如果计算与传输能够理想重叠，则：

$$
T_{token} \geq \max(T_{compute}, T_{transfer})
$$

如果不能重叠，则更接近：

$$
T_{token} \geq T_{compute}+T_{transfer}
$$

先比较真实结果距离这些边界有多远，再决定优化调度、减少数据量还是改变计算位置。

### 3.3 计算 break-even point

不要只问“方案是否更快”，还要问：

- 带宽低于多少时方案才有收益？
- 序列长度超过多少时 KV 成为主瓶颈？
- batch 多大时计算能够覆盖传输？
- 压缩率达到多少才能补偿解压开销？
- CPU 计算时间低于多少才值得异构执行？

研究贡献通常存在于这些边界和相变之中，而不只是某个单点的最好数字。

### 3.4 做敏感性分析

改变关键参数并观察结论是否稳定：

- PCIe/SSD 带宽；
- VRAM 容量；
- 模型层数和隐藏维度；
- prefill/decode；
- batch 和序列长度；
- Dense/MoE；
- CPU/GPU 相对算力；
- 传输与计算重叠程度。

只在一个配置下成立的结果，通常更像系统调参，而不是普遍机制。

## 4. 构建简单、快速、可信的验证系统

### 4.1 模拟器的第一目标是快速迭代

第一版模拟器只保留决定研究结论的变量。不要复刻整个 llama.cpp、CUDA runtime 或 FPGA 平台。

例如将每层表示为：

```text
LOAD_WEIGHT(i)
LOAD_KV(i)
COMPUTE(i)
SAVE_KV(i)
EVICT(i)
```

资源只保留：

```text
GPU compute engine
PCIe transfer engine
SSD I/O engine
VRAM slots
CPU workers
```

约束只保留：

- 数据准备完成后才能计算；
- 任务必须满足计算图依赖；
- 资源同一时刻容量有限；
- VRAM 占用不得超过上限；
- 数据最后使用前不得被覆盖；
- 同一 DMA/计算资源上的任务不能非法重叠。

### 4.2 逐级提高保真度

```text
解析模型
→ 离散事件模拟
→ Trace 驱动并校准
→ 周期级/RTL 模拟
→ 最小真实系统
→ 完整端到端系统
```

每一级都必须回答一个新问题。不能因为“以后总要实现”，就直接跳到最昂贵的一级。

### 4.3 用真实测量校准，而不是凭空设参数

模拟器中的带宽、延迟和计算时间应来自：

- 微基准；
- Nsight/perf 等 profiling；
- 真实系统 Trace；
- 硬件文档；
- 多次测量后的分布，而不只是峰值。

校准时不仅比较最终吞吐，还要比较：

- 每层执行时间；
- 数据搬运时间；
- GPU stall；
- PCIe/SSD 利用率；
- VRAM 峰值；
- prefill/decode 的不同趋势。

### 4.4 模拟器本身也需要验证

- 对极小例子手工计算结果；
- 构造带宽无限、容量无限等边界情况；
- 与解析模型的上下界比较；
- 用真实 Trace 回放；
- 报告误差而不是只展示相符的样例；
- 固定随机种子并保存配置；
- 让每幅图能够由一个命令重新生成。

## 5. 真实系统实现的准入条件

只有满足以下条件，才进入大型 C++、CUDA、llama.cpp 或 FPGA 实现：

1. 数学模型没有直接否定想法；
2. 模拟器能够解释真实系统的主要趋势；
3. 预测收益明显高于模拟误差和测量噪声；
4. 机制在多个合理配置下成立；
5. 已明确收益来自哪里；
6. 已确定真实实现要验证哪个尚未回答的问题；
7. 有最小侵入接口，不需要一开始重写整个系统；
8. 已设置实现时间上限和退出条件。

如果预测提升只有 5%，而模拟误差为 10%，就没有理由先进行数周系统实现。

## 6. LLM-Infer 的具体教训

当前实测数据包括：

- 每 token 权重流量约 `3.81 GB`；
- 有效 PCIe 带宽约 `5.66 GB/s`；
- 实际吞吐约 `1.3 token/s`。

由最简单的带宽模型：

$$
T_{weight}=\frac{3.81}{5.66}\approx0.673\text{ s/token}
$$

因此，只考虑权重传输时的吞吐上限约为：

$$
Throughput_{max}=\frac{5.66}{3.81}\approx1.49\text{ token/s}
$$

实际吞吐已经达到该上限的约 87%。如果策略不减少传输数据量、不提高有效带宽，也不改变计算位置，那么仅优化预取和调度的最大空间约为 15%。

这一计算本可以在大型系统实现之前完成。今后需要优先研究：

- 如何减少每 token 必须传输的数据量；
- 如何改变 CPU/GPU 的计算划分；
- 如何利用压缩、重计算、稀疏性或多请求复用；
- 如何将静态访问结构编译为全局执行计划；
- 什么条件下静态计划优于反应式 runtime；
- 如何处理 KV、请求和 MoE 带来的动态部分。

现有 llama.cpp 实现不再作为每个想法的第一实验场，而应作为：

1. 真实性基线；
2. Trace 和硬件参数来源；
3. 模拟器校准对象；
4. 最终候选机制的端到端验证平台。

## 7. 静态结构与动态执行

不要简单争论“静态图优于动态图”。应当拆分系统中的静态部分与动态部分。

LLM 推理中通常可以静态分析的内容包括：

- Dense Transformer 的层次和依赖；
- 权重访问顺序与大小；
- 大部分张量生命周期；
- 算子和数据搬运之间的先后关系。

必须保留动态性的内容包括：

- 请求到达；
- batch 和序列长度；
- KV Cache 的增长和物理位置；
- 运行时带宽波动；
- MoE 专家选择；
- 故障、抢占和资源竞争。

可能的研究范式是：

> 从静态计算骨架生成参数化、可执行、可验证的计划；运行时只处理不可避免的动态残差。

静态图是信息来源和优化条件，不应只作为实现标签或宣传用语。

## 8. FPGA 与硬件研究

### 8.1 不要用购买硬件代替问题定义

开始硬件项目之前，先问：

- 研究主张是否依赖真实板级行为？
- cycle-level 模拟能否回答当前问题？
- RTL 综合是否已经足以估算面积和频率？
- 购买开发板后，具体新增哪一条证据？
- 驱动、接口和工具链调试是否会掩盖核心机制？

如果这些问题没有明确答案，暂时不需要购买 FPGA。

### 8.2 推荐验证顺序

```text
算法/调度模型
→ 离散事件模拟
→ RTL 模块
→ Verilator 测试
→ 综合与时序报告
→ 必要时上板
```

FPGA 应用于验证物理实现可行性，而不是用于寻找研究问题。

## 9. 阅读论文的方法

不要以“读完某会议”为目标，而应围绕问题建立引用网络。可以重点观察 ISCA、ASPLOS、OSDI、EuroSys、MLSys、SOSP、PLDI、CGO 等会议，但分类依据应当是研究问题，而不是会议名称。

每篇论文记录：

1. 它解决的准确问题；
2. 关键观察；
3. 隐含和显式假设；
4. 静态信息与动态信息；
5. 核心机制；
6. 理论模型或性能模型；
7. 实验如何隔离变量；
8. 最接近的 baseline；
9. 哪些结果真正支持论文主张；
10. 放到自己的硬件和工作负载中，哪里会失效；
11. 有什么尚未解释的现象；
12. 与当前研究问题的关系。

阅读的输出应当是一张问题地图，而不是论文数量。

## 10. 判断创新性

在实现前搜索最接近工作，并制作对照表：

| 维度 | 最近工作 | 当前想法 |
|---|---|---|
| 问题定义 |  |  |
| 基本观察 |  |  |
| 调度粒度 |  |  |
| 静态/动态边界 |  |  |
| 硬件假设 |  |  |
| 优化目标 |  |  |
| 理论保证 |  |  |
| 系统机制 |  |  |
| 评价指标 |  |  |

以下内容通常不能单独构成创新：

- 把已有机制移植到另一个框架；
- 调整固定参数；
- 将 layer 粒度简单改成 tensor 粒度；
- 使用静态图、异步流或双缓冲；
- 换一套硬件后重复相同结论；
- 只比一个较弱 baseline 更快；
- 工程量很大，但没有新的观察或抽象。

可以构成研究贡献的内容包括：

- 新的、可重复的系统观察；
- 新的问题定义；
- 新的理论边界或不可能性结果；
- 能统一解释多个现象的模型；
- 打开新设计空间的抽象或 IR；
- 在重要约束下获得新的 Pareto 点；
- 将经验策略转化为可编译、可验证的计划；
- 揭示现有机制只在特定区域有效，并给出边界。

## 11. 实验设计纪律

- 一次实验只回答一个主要问题；
- 先定义指标，再运行实验；
- 区分机制收益与工程优化收益；
- 保存硬件、软件版本、参数、随机种子和命令；
- 同时报平均值、方差和尾部行为；
- 不只选择有利工作负载；
- 解释异常值，不删除不符合预期的数据；
- 做 ablation，确认每个组件是否必要；
- 与理论上限、简单策略和最强相关工作比较；
- 在写代码前设计最终希望出现的图表及其含义；
- 失败实验也要记录假设、配置、结果和结论。

## 12. 时间与止损规则

### 12.1 三天证伪规则

一个早期想法应尽量在三天内通过以下方式得到初步判断：

- 纸笔模型；
- 小脚本；
- 微基准；
- Trace 分析；
- 最小模拟器；
- 文献对照。

三天内无法验证时，优先缩小问题，而不是扩大工程。

### 12.2 分阶段准入

每阶段结束后明确选择：继续、修改或停止。

```text
观察成立？
→ 模型允许显著收益？
→ 模拟结果稳定？
→ Trace 能够校准？
→ 最小原型有效？
→ 值得完整实现？
```

只有前一问题得到肯定回答，才进入下一阶段。

### 12.3 不同时经营多个大型交付物

数学、论文阅读、一生一芯、SAIR、LLM-Infer、导师 FPGA 项目可以长期并存，但同一阶段只能有一个主要研究交付物。其余内容应当作为课程、练习或受控支线，不能同时要求达到论文级完成度。

## 13. 与导师合作

导师的建议不一定正确，但不应仅凭直觉拒绝。出现分歧时，应当：

1. 复述自己对建议的理解；
2. 写清各方案要回答的问题；
3. 比较时间、风险和最小产出；
4. 用小实验检验分歧；
5. 定期汇报证据，而不是只汇报实现进度；
6. 在证据变化后及时更新判断。

汇报时优先采用：

```text
本周验证的假设
→ 使用的方法
→ 得到的证据
→ 与预期不符之处
→ 下一步最便宜的验证
→ 需要导师判断的问题
```

不要只汇报“实现了多少文件、解决了多少 bug”。

## 14. 对失败和后悔的处理

- 判断错误不等于不适合科研；
- 被批评不等于研究能力已经被判定；
- 工程走弯路后，应提取 Trace、数据、工具和失败边界；
- 不通过继续堆代码来证明此前选择正确；
- 不把一次项目失败上升为对人格和未来的判断；
- 真正重要的是能否根据新证据更新认识；
- 休息不是逃避，情绪强烈时不做长期路线决策。

过去的实现可以转化为校准基线和反例。已经付出的代价无法撤销，但可以改变它在未来研究中的用途。

## 15. SAIR 作为方法训练项目

SAIR 若作为磨刀项目，应先实现受控的语言内核，而不是通用创作平台或完整 Code Agent：

```text
文本 DSL
→ Parser
→ AST/图 IR
→ 静态检查
→ 解释执行
→ Trace/检查点/可视化
```

它可以训练 Rust、编译原理、图算法、类型/效果系统和状态机。第一版不需要多 Agent、模型路由、TUI、互联网搜索或 Lean 集成。

SAIR 与 LLM-Infer 的共同母题是：

```text
SAIR：静态任务结构 → 可验证计划 → 动态 Agent 执行
LLM-Infer：静态计算结构 → 可验证存储计划 → 动态推理执行
```

共同问题是：哪些结构可以提前描述、分析和验证，哪些不确定性必须留给运行时。

## 16. 开始实现前的最终检查表

### 研究问题

- [ ] 我能用一句话说清观察吗？
- [ ] 观察有证据，而不只是直觉吗？
- [ ] 我能用一句话说清机制吗？
- [ ] 已找到最接近的三到五项工作吗？
- [ ] 差异是研究差异，而不只是框架或语言差异吗？

### 模型与验证

- [ ] 计算过容量、带宽和算力上界吗？
- [ ] 计算过理想情况下的最大端到端收益吗？
- [ ] 找到 break-even point 了吗？
- [ ] 做过关键参数的敏感性分析吗？
- [ ] 定义了什么结果意味着停止吗？
- [ ] 能否先用三天内完成的实验验证？

### 实现

- [ ] 真实实现具体要回答哪个模拟器无法回答的问题？
- [ ] 是否存在更小的原型？
- [ ] 是否可以通过稳定接口替换策略，而不侵入整个系统？
- [ ] 是否设置了时间上限？
- [ ] 如果实现失败，仍能留下什么可复用产物？

### 实验与论文

- [ ] baseline 足够强且公平吗？
- [ ] 指标与论文主张直接对应吗？
- [ ] 能区分机制收益与调参收益吗？
- [ ] 实验是否可复现？
- [ ] 结果不理想时，是否仍能得到清楚的科学结论？

## 17. 一句话提醒

> 先问问题，后做系统；先算上界，后调参数；先快速证伪，后长期实现；先找到新的观察和抽象，再让工程为它提供证据。
