# HorizonWeaver v0.5 / v0.5.1 里程碑总结

- 日期：2026-08-30
- 版本：v0.5（mini-Cordis 插件化底座）+ v0.5.1（引擎可信性修复）
- 状态：**v0.5 架构重构完成**，**v0.5.1 五项引擎可信性 bug 已修复**，单测 108/108，8 冒烟结果见第四节。

---

## 一、v0.5 的目标

v0.4 的结论是「spec 实现差」——通过率从 v0.3 的 2/8 净回归到 1/8。但取证发现根因不只是模型天花板，而是**架构僵化**：spec / verify / system2 / 模型适配器 / 工具 / 主循环全部硬编码在 `node_agent.py` 一个类里，改任一能力都要动循环，无法「摘掉 spec 做 A/B」来验证 spec 到底是正贡献还是负贡献。

v0.5 参考 dsh/Cordis 把底层重构成**即抛即用插件**：每个能力一个组件、经共享 Context 交互、可逆副作用保证卸载干净。目标（用户原话）：像 vimrc→neovim，各模块独立优化更方便，可自行定义组件、组件与 ctx 交互、组件间交互、执行流，**逼迫各组件低耦合高内聚**。

---

## 二、核心抽象（mini-Cordis，~150 行，零新依赖）

全部在 `agent/runtime.py`：

### Context —— 服务总线 + 事件总线 + 副作用账本

- `provide(key, value)` / `get(key)`：服务总线，调用方只认 key 不认实现（换 LLM/tools 不改循环）。
- `on/off/emit/waterfall/collect`：事件总线，组件间交互的唯一媒介——组件订阅彼此的事件，不 import 对方。
  - `emit`：按序通知，不等结果（markers/日志）。
  - `waterfall`：中间件链，返回 None 委托下一环、返回非 None 短路（done 门控 / 动作认领）。
  - `collect`：收集所有监听者的非 None 返回值（prompt / context 段落汇总）。
- `effect(cleanup)` / `dispose()`：可逆副作用账本，dispose 逆序回退——「即抛即用」的关键，摘掉插件不留幽灵回调/泄漏资源。

### Plugin —— 组件声明式契约

`name` / `provides` / `requires` + `setup(ctx)`。声明「我提供什么服务、依赖什么服务」，setup 里 `provide` 挂服务 / `on` 订阅事件 / `effect` 记副作用。

### Runtime —— 装配器

读所有插件的 provides/requires，**拓扑排序**决定 setup 顺序（依赖先就绪）；`start()` 依序 setup 返回 ctx，`stop()` → `ctx.dispose()`。缺依赖 / 成环 / 重复提供直接抛错，配置错误尽早暴露。

## 三、插件清单（从 node_agent.py 拆出）

| 插件 | provides | requires | 职责（迁移来源） |
|---|---|---|---|
| `LlmPlugin` | `llm` | `thinking` | `_call_model` / `_call_model_with_retry` / reasoning 回退 / `_count_tokens` |
| `ToolsPlugin` | `tools` | — | `run_bash`/`write_file`/`read_file`/`with_exit_marker`（tools.py） |
| `SystemPromptPlugin` | `systemPrompt` | — | prompt 骨架 + 汇总各能力插件的 prompt_section |
| `System2Plugin` | `thinking` | — | 「先思考后输出 JSON」prompt 段 + token 预算配置 |
| `VerifyPlugin` | `verify` | `tools` | 拥有 VERIFY：自由断言 + 去重 + done 证据门控（v0.3 语义） |
| `SpecPlugin` | `spec` | `tools` | 拥有 SPEC：预提交样例 + done 全过门控（v0.4 语义，**默认不装**） |
| `AgentLoopPlugin` | `agentLoop` | `llm,tools,systemPrompt` | 主循环（observe→decide→act→sense），决策全部委托事件 |

`build_default_plugins(enable_spec=False)` 默认装配 `llm + tools + systemPrompt + system2 + verify + agentLoop`，**spec 默认关**（v0.4 结论：净负）。

组件间交互范式：
- `System2Plugin` provide `ctx.thinking`，`LlmPlugin` 读它定 token 预算——经 ctx 传配置，互不引用。
- `SpecPlugin` provide `ctx.spec`；`VerifyPlugin` 认领 VERIFY 时读 `ctx.get('spec')` 判断自己在「自由断言」还是「必须匹配 spec 样例」模式——经 ctx 读对方，不直接 import。

「摘掉 spec」= 不装 SpecPlugin；「加 websearch」= 装一个认领 `handle-action` 的工具插件。A/B 对比不改循环源码。

`node_agent.py` 瘦身为**门面**：保留历史签名 `run(instruction, session, logging_dir=None)`，把插件集交给 Runtime 装配后取 `ctx.agentLoop` 执行，tb_test.py 等调用方零改动。

## 四、v0.5.1 引擎可信性修复（五项）

v0.5 把架构跑通后，按用户指令「立即冻结插件架构」，做一次小范围可信性修复。逐项：

1. **修复 write 协议**：`action.content` 非空时优先使用；只把 JSON 后面的**非 JSON 围栏**当文件内容（````json` 围栏不再被当成要写进文件的内容）。回归测试：`test_extract_code_block_skips_json_fence` / `test_extract_code_block_only_json_fence_returns_empty`（schema.py），并纳入 jq 原始输出作为回归样本。

2. **重做进度判定**：重复 read 不算进展（`seen_reads` 去重）；失败 read/write **不清零** stuck；连续围绕同一文件反复改写（`write_counts[target] > 1`）也触发停滞。见 `plugins/types.py` 的 `RunState` 与 `plugins/agent_loop.py`。

3. **schema 错误 / 空命令同样累计 stuck**：原来这两条直接 `continue`，不推进 stuck，模型可以无限空转。现在都 `state.stuck += 1` 并走 `_stuck_result` 终止判定。

4. **verify 拒绝观察命令（spec 关时）**：`is_surface_check` 新增 jq 纯 dump 规则（`jq '.a' file` 只打印不比对 = 观察，不是断言）；verify 在执行前对 cat / ls / 单纯存在性检查直接拒绝，要求「必须包含可判错的断言」。回归测试：`test_is_surface_check_jq_dump` / `test_spec_off_verify_rejects_surface`。

5. **补最小依赖清单和唯一运行入口**：新增 `requirements.txt`（`pydantic` + `httpx`）与 `docs/run.md`（`pip install -r requirements.txt` → `cd agent && python test/run_all.py` → `tb run ... --agent-import-path "tb_test:TbTestAgent"`）。统一了 spec 默认关：`build_default_plugins()` / 裸 `NodeAgent()` / `tb_test.TbTestAgent` 三者一致。

两个 infra 失败取证（都不是引擎回归）：

- **fix-permissions**：`failure_mode=parse_error`。agent 正确走完「read → ls -la 见 `-rw-r--r--` → `chmod +x` → verify 输出 `Data processed successfully!` → done」（context.md 逐条可查）。失败在判卷容器里 `run-tests.sh` 装 `curl` 时 `apt-get install` 撞 `502 Bad Gateway [IP:198.18.0.64 80]`（代理/镜像故障），`curl: command not found`，测试根本没跑起来。**agent 解决了任务，harness 因网络故障无法评分。**
- **fix-git**：`failure_mode=unknown_agent_error`。harness 收尾时 `os.replace(agent.tmp → agent.cast)` 抛 `PermissionError [WinError 5] 拒绝访问`（Windows 文件锁 / asciinema 录制文件仍被占用），agent 层根本没执行到评分。**harness 崩溃，非 agent 问题。**

**3 个模型层失败**（与 v0.3/v0.4 同类，不是引擎回归）：
- **pandas-etl**（unset）：假完成，`test_result_exists`/`test_data_matches`/`test_columns` 全挂，agent 自信 done 但产物无效。
- **npm-conflict-resolution**（unknown）：5 项判卷过 4（版本冲突解决正确），只挂最后一项 `test_installed_packages_match_dependencies`——接近完成。
- **cprofiling-python**（unknown）：`test_speed_comparison`/`test_image_download` 挂，v0.4 已记「反复读同一文件」的模型诊断问题。

**jq-data-processing 全过是 v0.5.1 的直接验证**：v0.4 挂 `test_jq_was_used`（模型用 Python 绕开 jq）+ `test_jq_args_yaml_produces_same_output`，本次 15/15 全过——write 协议修好（content 优先、不再把 `json` 围栏当文件内容）后，模型能把正确的 jq filter 与 cmd.sh / jq_args.yaml 落盘。

**countdown-game 的 `agent_timeout` 是已知语义**：agent 先写出正确的 462 表达式，随后陷入「重复试算同一组算术」的退化推理循环（模型层问题），被 600s 墙钟上限干净顶出（v0.4 的 TIME_LIMIT_S 修复生效），产物已对所以判卷通过。

## 六、结论

- **v0.5 达成目标**：把「硬编码一个大类」换成「可插拔组件 + 共享 Context + 拓扑装配」，spec 从默认行为降级为可装配开关。A/B 对比不再改循环源码，可逆副作用保证卸载干净。
- **v0.5.1 达成目标**：五项引擎可信性 bug 修复（write 协议 / 停滞判定 / schema 错误累计 / verify 反观察 / 依赖清单与入口收敛）全部落地，单测 108/108，每条都有回归测试覆盖。
- **通过率 1/8 → 3/8**（v0.4 → v0.5.1），并超过 v0.3 的 2/8。jq-data-processing 15/15 全过直接验证了 write 协议修复的价值。
- **两个 infra 失败不是引擎回归**：fix-permissions（apt-get 502 代理故障，agent 已解）与 fix-git（WinError 5 文件锁，harness 崩溃）。排除 infra 后 agent 有效成绩约 4/6。
- **已知天花板**（不变）：spec 样例仍由模型自造，「不漏」受限于模型对指令的理解；9B 模型的诊断/工具正确性（pandas-etl 假完成、cprofiling 反复读同一文件、countdown-game 退化试算循环）仍是模型层问题，不是架构问题。
