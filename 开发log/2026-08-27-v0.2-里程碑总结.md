## 一、v0.2 的目标

v0.1 用数据坐实了三个架构缺陷：

- **P0-1 回环检测空转**：`_state_key` 只把重复命令标 `REFUTED`，既不阻止重执行、也不强制换思路（`broken-python` 100 步只有 16 条不同命令）。
- **P0-2 过早 done**：`fix-permissions` 只跑 `cat`+`bash` 两步就报完成，无任何产出证据。
- **P1 多行命令被破坏**：heredoc 被 harness 的 `; tmux wait -S done` 追加进正文导致 `SyntaxError`。

v0.2 的目标是把「换路 / 验证 / 回滚」从**模型自律的软约束**升级为**引擎级的硬保证**。设计对齐分三层：

| 层面 | 参考对象 |
|---|---|
| 设计思路 / 价值观 | DeepSeek Harness（框架级保证，而非提示词自律） |
| 工具调用机制 | Claude Code（validate→execute→result + 退出码/验证） |
| 循环 / 编排 | 自己的六步循环 + dsh 三条铁律 |

## 二、架构实现

### 2.1 总览：六步循环 + 工具化 + 图结点

核心是 **结构化输入输出（模型只吐一个 Action JSON）+ 图导航规划**，跑在一个六步循环上：

```
observe(读终端) → decide(模型出 Action JSON) → act(按 tool 执行)
→ sense(读新终端) → update(落图结点) → loop-closure(去重/卡死判定)
```

整个循环由 `keyan_agent.py::perform_task()` 驱动，每一步 action 落一个 `Node` 到 `logging_dir/graph/nodes.jsonl`（append-only，会话日志是唯一真相）。

### 2.2 文件结构

| 文件 | 作用 |
|---|---|
| `agent/schema.py` | 结构化 I/O：`Action`/`Node`/`ActionKind`/`ToolKind` 定义 + `parse_action`（严格校验弱模型易吐的非法 JSON） |
| `agent/tools.py` | 工具层（对齐 Claude Code）：`bash`/`write`/`read`/`verify` + 退出码哨兵注入/解析 |
| `agent/keyan_agent.py` | Terminal-Bench 适配器（`BaseAgent` 子类），六步循环 + done 门控 + 去重/卡死判定 |
| `agent/system_prompt.py` | system prompt 内核（图导航 + 科研规则 + 动作 schema 语义） |
| `agent/loop.py` | 独立版六步循环（有 git 的真 rollback，非 Terminal-Bench 路径） |
| `agent/test_v02.py` | 单元测试（23 条，只依赖 schema/tools，离线可跑） |

### 2.3 数据结构（schema.py）

**动作块 `Action`**（模型每次输出一个）：

| 字段 | 含义 |
|---|---|
| `action` | 五选一：`act`（做变化）/ `verify`（客观断言检查）/ `rollback`（回退）/ `retrieve`（按需加载上下文）/ `done`（声称完成） |
| `tool` | 仅 `action=act` 生效：`bash`（单行命令）/ `write`（写文件）/ `read`（读文件） |
| `target` | 动作对象：bash=命令；write/read=容器内绝对路径；verify=检查命令 |
| `content` | 已弃用（write 的文件内容放在 JSON 之后的 ``` 围栏代码块里，避免多行塞进 JSON 字符串导致解析失败） |
| `change` | 一句话客观说明（写入结点 `changes`） |
| `reasoning` | 主观因果推断「这步变化 → 预期结果」（写入结点 `inference`） |

**图结点 `Node`**（写进 nodes.jsonl）：

- 客观字段：`index`（指标）、`changes`（客观变化）、`git`（git 状态）——由 harness 测量，模型不填；
- 主观字段：`inference`（模型推理的因果映射，只用于规划，不用于判定结点好坏）；
- v0.2 新增：`exit_code`（该步退出码，0=成功）、`verified`（是否「已通过」的 verify，done 门控证据）。

### 2.4 工具层（tools.py，对齐 Claude Code）

四类动作对应四种工具，核心是把「裸 `send_keys` 发命令」升级成带退出码的执行路径：

| 工具 | 实现 | 退出码 |
|---|---|---|
| `bash` | `send_keys` 执行单行命令，命令尾注入退出码哨兵 | 从输出解析 `KEYAN_EXIT_CODE=N` |
| `write` | `copy_to_container`（put_archive）写文件——绕开 heredoc，正对 P1 | 0（成功）/ `None`（失败） |
| `read` | `cat "路径"`（观察，可重复，不参与去重） | 同 bash |
| `verify` | 本质是 `bash`，但强制记录退出码并写进结点 `verified`/`exit_code` | 0 → `verified=True` |

**退出码哨兵机制**（唯一直接拿退出码的通道）：

1. `with_exit_marker(cmd)` 在命令末尾注入 `; echo 'KEYAN_EXIT_CODE='$?`——它在 harness 追加 `; tmux wait -S done` **之前**，所以 `$?` 捕获的是原命令真实退出码；
2. 执行后 `parse_exit_code(out)` 取输出里**最后**一次 `KEYAN_EXIT_CODE=N`；
3. **B8 关键**：模型会偷学哨兵，自己在命令里写 `; echo 'KEYAN_EXIT_CODE='$?`，产生第二个恒为 0 的伪哨兵把真实退出码掩盖。`with_exit_marker` 因此先用 `_SELF_ECHO_RE` 剥掉模型自注入的哨兵，保证只剩 harness 那一个。

### 2.5 主循环的三个硬保证（dsh 三条铁律的 Python 落点）

**铁律 A（可回退效应）→ rollback 信号**：容器内无 git 控制权，`rollback` 转成强信号注入「用 act+write 把上一步改回去，不要空转」。

**铁律 B（反应式 coeffect）→ 去重 + 卡死终止**：三张去重表 `seen_commands`（bash 命令→退出码）、`seen_verifies`（verify 命令→退出码）、`seen_writes`（target+内容 sha1）。重复执行 → 拒绝并 `stuck += 1`；连续 `STUCK_LIMIT=8` 步无进展 → 干净终止（`FailureMode.UNKNOWN`），不再烧满 100 步/900s。

**铁律 C（日志是唯一真相）→ done 门控**：`done_gate_rejection` 要求 (1) 超过 `MIN_STEPS_BEFORE_DONE=2` 步 (2) 至少一次 `verified=True 且 exit_code==0` 的 verify 证据，否则拒绝 done。

### 2.6 system prompt 内核

`system_prompt.py` 拆成两层复用：

- **共享内核**（`CORE_KERNEL` + `RESEARCH_RULES`）：图导航协议、结点三分（index/changes/inference）、项目自主导航、精确上下文管理、最小验证原则、科研原则 10 条硬规则——对 Terminal-Bench 适配版与独立版 `loop.py` 一致；
- **载体专属段**（`_TERMINAL_ACTIONS`）：动作 schema 语义 + 8 条硬规则（一次一个动作、命令只执行一次、多行走 write、不自 echo KEYAN_EXIT_CODE、done 前必须有 verify 证据、重复会被拒绝并计入卡死等）。

## 三、v0.2 修复清单（B1–B8）

| 编号 | 缺陷 | 修复 | 位置 |
|---|---|---|---|
| B1 | 尾随围栏代码块破坏 JSON 提取（`首 { 到末 }` 会把 write 的文件内容也当 JSON） | `_extract_json` 用括号配对取第一个完整对象；write 内容从 ``` 围栏代码块取（`extract_code_block`） | schema.py |
| B2 | 非 act 动作带 `tool="none"/"N/A"` → ToolKind 枚举校验失败卡死 done | `_normalize_action` 丢弃非 act 动作的 tool 字段 | schema.py |
| B3 | verify 失败不推进度 → 反复 verify 空转 | verify 失败 `stuck += 1`，纳入卡死判定 | keyan_agent.py |
| B4 | Windows `pathlib.Path` 把容器路径 `/app` 判成非绝对 → write 全被拒 | `write_file` 用 `PurePosixPath` + `path.startswith("/")` | tools.py |
| B5 | 相同命令/内容反复执行烧满 900s | bash 按命令、verify 按命令、write 按 target+内容 sha1 去重，重复拒绝并计入卡死 | keyan_agent.py |
| B6 | verify 写成「运行脚本 && echo」，假退出码 | 提示词澄清 verify 是客观断言（`test -f`/`grep -q`/`python -c "assert"`），并明令不自 echo KEYAN_EXIT_CODE | system_prompt.py |
| B7 | retrieve/rollback 静默 `continue` 不落结点不计卡死，反复空转烧满 max_steps | retrieve 带 target 转 read；retrieve 无 target / rollback / done 拒绝都计入卡死 | keyan_agent.py |
| B8 | 模型自注入 `; echo 'KEYAN_EXIT_CODE='$?` 使真实退出码被伪哨兵掩盖成 0 | `with_exit_marker` 用 `_SELF_ECHO_RE` 剥离自注入哨兵，只剩 harness 的 | tools.py |

### pandas-etl 解题路径（首个通过）

`retrieve→read /app/data.csv` → `write process.py` → 诊断环境（`pip install pandas` exit=127、`apt-get install` 失败）→ `write transform.py`（**改用纯 `csv` 模块绕开缺失的 pandas**）→ `python3 transform.py` exit=0 → 多轮 `verify` 客观断言 `/app/result.csv` 通过 → 隐藏测试判定 resolved。

这正是 v0.2 设计的预期路径：工具化 write 落脚本、退出码反馈真实失败、verify 提供 done 证据。

### 新观察（非引擎缺陷，属模型能力上限）

`countdown-game` 解不出时「随机游走不收敛」：`retrieve→read`、`read`、`write-不同内容` 都会把卡死计数 `stuck` 归零，且都算「新动作」不被去重，于是「连续 8 步无进展」永远不触发，只能靠 harness 900s 超时兜底。这与 B1–B8 不同——不是「重复自己」（可被去重拦），而是「打转」（每次 write 确实是新内容），引擎层面无法廉价区分「真探索」与「打转」。

**附带一个 harness 现象**：900s 超时后日志仍在继续写——同步 `perform_task` 跑在 executor 线程里，asyncio 超时无法干净取消它。这是 terminal-bench「同步 agent + asyncio 超时」的固有矛盾，不在 keyan_agent 可修范围。

## 五、结论与 v0.3 方向

**v0.2 达成了目标**：P0-1/P0-2/P1 三个架构缺陷全部升级为引擎级硬保证（去重、卡死终止、done 门控、退出码如实上报），并产出首个通过的任务（`pandas-etl`）。

剩余 0% 已与架构解耦，坐实为 **9B 模型能力天花板**——模型能正确观察到失败（pip 坏、缺 pandas），但往往诊断不到根因、或解不出复杂任务。这与 v0.1 的结论一致，是「模型弱」与「架构弱」分离评估的第二层问题。

### v0.3 候选方向（待定）

1. **模型侧**：试 `--reasoning-format deepseek`（保留推理但正确路由，避开空 content），或换更强模型跑同一冒烟集，单独评估模型能力上限。
2. **卡死判定的对称性**：探索「真探索 vs 打转」的区分（如给 read/retrieve/write 也设去重阈值），但要先论证不会误杀合法探索。
3. **prompt 增强**：把 pandas-etl 的「绕开缺依赖」成功路径提炼成提示（如「环境缺包时先用标准库替代」）。
4. **回滚真实现**：独立版 `loop.py` 的 git 真 commit/checkout 回退链（dsh 铁律 A 的完整落点）。
