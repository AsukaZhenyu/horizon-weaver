## JQ：候选正确，四项自建调用不正确

原生 TB **14/14**；**no_progress，21 步，259.9 秒**，dev12 同任务是 no_progress / 268.1 秒。没有 done 动作，也没有被拒绝的提交。

第 9 步四项 process 检查均失败：

- verify_output 把 shell 外层单引号和多余的右括号作为 jq 参数的一部分，又把 `/app/active_users_report.json` 文件路径当作预期 stdout 字符串。
- 两项 yq 检查把 `'.args[]'`、`'.filter'` 的 shell 引号作为参数内容，实际解析失败。
- verify_replay 把 `$(yq ...)` 分成字面 argv。process 不启用 shell，无法做命令替换，jq 收到的是这些字面字符。

模型将原因解释为产物 YAML 格式或 jq 业务表达式错误，随后调整候选、执行重复命令，第 16/20 步重跑同一批定义，均再次失败。两次保存 ID 重测确实发生，12 项执行回执全部失败。检查代码取回接口已交付，但 Policy 没有发起 check_id 查询，也没有显式纠正检查。八次有证据引用的认识更新文本互不相同，仍未形成正确诊断；不同措辞不能作为策略改变的证据。

因此剩余问题是 **Policy 生成、理解并纠正检查调用的能力**。新 Python 语法入口不会判断 jq/yq 的参数语义或预期 stdout 的目标相关性。本轮没有 Python 定义语法错误，不能把真实模型收益归因于这一项入口修复。它的边界由机制回归验证；修改候选不会自动解除旧反例，也不会把调用失败当作客观任务验收。
