## 为什么重复仍然增加

8 项共 52 条带执行证据引用的认识更新；空白归一后的 current_problem、interpretation、next_focus 三字段只有 23 组不同文本，29 条重复已有文字。不同措辞也不能证明新增洞见。该度量见 extra-metrics.json。

异步任务第 2 步的自检在 import 时遇到 unmatched '}'，没有到达断言。修复后多次认识仍沿用这条旧语法诊断，提出同内容写入；总计 14 次零变化写入提议。最终外部 5/6，仍没有实现超过上限的取消语义。保存并引用旧事实，不代表它仍描述当前候选；文件变化标记不足以更新模型的因果解释。

日志第 11 步 text_equals 的预期包含标题和 ERROR/WARNING/INFO 顺序，当时产物无标题且顺序不同。后续产物已经修到外部 3/3，但模型继续声称缺标题、再次写入同一内容，没有取得当前版本的重新测量。8 条认识更新伴随 7 次零变化写入提议，最终 no_progress，约 206 秒，明显高于 r12 正常提交的 61 秒。历史失败应当保留，同时须明确它是当前反例还是修复后的待重测项；目前工作集对后者的表达仍不够有效。

Regex 第 3 步自检因重复命名组 date 而崩溃。便签识别了重名问题，但后续多次输出相同模式，未完成对应修复。外部 0/1、301 秒超时。自建样例的预期还存在未经公开要求确认的内容，证明执行检查与选择可靠预期仍是不同能力。

profiling 反复运行相同 pip 安装命令并遇到 SSL EOF。便签知道依赖安装失败，却没有找到可行的新方向。最终 fast.py 为空，fastest.py 未生成；没有结构化验证收据。原候选补评分为 0/2：速度测试执行时找不到 fastest.py，图像检查没有所需下载产物。此任务存在真实网络障碍，不能把总耗时与产物变化全部归因于上下文修改。

SQLite 多次普通查询后检查二进制，随后尝试自建恢复解析器，最终 recover.json 为 []。没有实际证明自己的页布局解释，亦没有结构化验证收据。该候选与原始 trunc.db 已按完整快照保存；原候选补评分为 0/1，实际匹配到 0 条恢复数据，未达到原测试要求。

## Verify 已实现什么，仍缺什么

执行结果、预期、来源和覆盖主张分开存储。预期修订需要显式替换关系、相关公开来源与依据、当前通过的比较；固定合同 oracle 不能改。负对照改为可选，避免将严格流程当成客观性。权限任务实际走通了这一机制。

Python 非常量谓词只是粗筛：存在变量引用不能证明比较了真正的候选行为。公共来源行号也只是来源位置，不能自动赋予正确预期或完整覆盖。任务要求表仍由 Policy 选择，TB 的 expected_artifacts 未自动填充；当前结构不能保证每项交付物与关键行为都有验证。

本次 0 次被阻塞提交，不能解释为所有完成问题已解决：日志和 JQ 没有提出正常提交，异步/Regex/SQLite/profiling 超时。正常提交且整项通过仍为 2 项，只是由 Hello+日志变为 Hello+权限。

## 后续应验证的改动方向

继续在现有 StateQuery/ContextCompiler 中，把当前产物事实、最后一次真实测量、测量后的改动和旧解释分开展示；将“已修复，待重测”显式呈现，避免旧失败仍被当成当前观察。保持最近完整读取与拒绝反馈的共同可见性，解决读—拒绝—再读交替。

Policy 的小便签应回答“本次新观测改变了什么，哪项解释仍未被验证”，并将下一行动连接到待取得的证据。无需再增加 Agent 或通用固定解题流程。认识更新本身不算进展，反复复制不能用作质量达标证明。

Verify 继续围绕公开目标的关键行为构造测量，保留失败历史及来源，但帮助 Policy 区分修复候选、修正预期、环境障碍和未知原因。检查与对应任务义务的关联及实际测量要一起展示；不能仅凭一次窄检查通过宣布任务完成。

这些是本轮记录支持的后续方向，尚未加入本轮受测源码。当前机制回归通过，准确率、重复和效率的任务层优化仍未通过验收。
